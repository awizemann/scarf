# Hermes Version Compatibility

Scarf reads Hermes's SQLite database directly and parses CLI output from `hermes status`, `hermes doctor`, `hermes tools`, `hermes sessions`, `hermes gateway`, and `hermes pairing`. It also speaks ACP (`hermes acp`) for chat. Compatibility comes from automatic schema detection plus tolerant parsing.

## Currently targeted

**Scarf v2.20.0 targets Hermes v0.20.4 "Herald" (v2026.8.18) — verified via a source-audited v0.20.0→v0.20.4 delta (~3,000 commits over four patch tags).** The eight-surface audit found `state.db` effectively additive (SCHEMA_VERSION 25→26; `messages`/FTS/`session_model_usage` byte-identical, `sessions` gained `hidden`/`last_read_at`/`title_source`/`git_metadata_generation` — the first two schema-detected and adopted) and the ACP wire clean. Three would-be breakages were fixed ahead of the host upgrade: the 14 built-in personalities moved out of `config.yaml` into Hermes code (Scarf now carries them in-code too, unioned with user entries, and fixed two pre-existing parse bugs that had the Personalities list broken since inception); v0.20.4's cron firing gate refuses jobs with pause markers, so ScarfGo's enable toggle now drives `hermes cron pause|resume` with full resume semantics; and `skills update` silently skips locally-edited skills, which Scarf now reports (with per-skill, explicitly-confirmed `--force`). Adopted v0.20.4 surfaces, all patch-gated (`isV0204OrLater`, 8 flags) or column-probed: unread session indicators (Hermes `session_unread` watermark semantics incl. the messages-max term), hidden-session filtering, reset-child session listing, curator ledger / purge / per-entry rollback, repo-local project skills + trust, the 20-server optional-MCP catalog picker, MCP `identity_header`/`strict_redirect_headers`/stdio-`cwd` (validation matching Hermes's), the new Actual Computer provider + `openai-codex` label rename, top-level-precedent `multiplex_profile_allowlist` parsing (fails closed like upstream), and ~10 new config keys (wake-word capture, STT trimming/idle-unload, `auxiliary.background_review.enabled` kill switch, concurrency + timeout knobs). Pre-0.20.4 hosts render byte-identically — proven by degradation tests.

**Scarf v2.18.0–v2.19.2 targeted Hermes v0.20.0 "Herald" (v2026.8.3) — verified via a source-audited v0.18.2→v0.20.0 delta (~5,700 commits spanning v0.19 "Quicksilver" and v0.20 "Herald").** The audit found `state.db` SCHEMA_VERSION moved 19→25 but every column Scarf queries was untouched — all additions are additive (`messages.effect_disposition`/`api_content`/`display_kind`/`display_metadata`, `sessions.pinned`/`last_activity_*`/`profile_name`, new tables `system_prompts`/`session_model_usage`/`async_delegations`/`delivery_obligations`); the ACP method roster and `session_update` discriminators are byte-identical across the delta. Forced changes: **`/compact` renamed `/compress`** (Scarf follows suit on 0.20 hosts, keeps `/compact` on older ones — never both); the `curator status` header text changed generations (Scarf's parser now accepts both); the provider catalog picked up **Vercel AI Gateway** (back, with aggregator handling), **Fireworks AI** and **Google Vertex AI** (overlay-only), a Solar→Upstage alias, and retired-DeepSeek (`deepseek-chat`/`deepseek-reasoner`) → `deepseek-v4-flash` resolution; **Buzz** (Block's Nostr-based messenger) joined the gateway platform roster (user-gated via `allowed_users`, no allowlist-kind mapping); `agent.max_turns`'s display default follows the connected host (60 pre-0.20, 500 at 0.20+, never baked into the parser). New v0.20-gated surfaces: pinned sessions + last-activity descriptions in the chat sidebar, per-model cost breakdown on the Dashboard, richer session export (Markdown/HTML/Quarto/trace + secret redaction, schema-gated to stdout-only formats on remote hosts), `approvals suggest` allowlist proposals in Settings → Security, and cron run history. Scarf v2.19.0 closed the remaining Hermes 0.20 settings backlog (title generation, per-task reasoning effort, smart approval policy, secrets sources, voice STT/TTS tuning, telemetry + SQLite journal knobs, `gateway.profile_routes` routing editor) and fixed a long-standing bug where the browser backend picker wrote `browser.backend` — a key that never existed in any Hermes version; the real key is `browser.cloud_provider`. The same two-cycle audit caught five other pre-existing bugs, all fixed: `skills uninstall`/`update` passed a nonexistent `--yes` flag (Skills UI uninstall/update had never worked); the "runtime metadata footer" toggle wrote `agent.runtime_metadata_footer` instead of the real `display.runtime_footer.enabled`; Google Chat and Microsoft Teams used the wrong platform ids (`google-chat`/`microsoft-teams` vs Hermes's `google_chat`/`teams`); per-platform `busy_ack_enabled` was a silent no-op (Hermes only reads the global `display.busy_ack_enabled`); and a "slash command notice TTL" setting wrote a key that doesn't exist in any Hermes version. Every new surface is capability-gated through `HermesCapabilities`; pre-0.20 hosts render exactly as before.

## How compatibility is maintained

**SQLite schema detection.** [`HermesDataService`](Core-Services) probes for v0.7+ columns (`reasoning_tokens`, `actual_cost_usd`, `cost_status`, `billing_provider`) and v0.11+ columns (`sessions.api_call_count`, `messages.reasoning_content`) at open time. The v0.11 flag (`hasV011Schema`) only flips true when both new columns are present — partial-migration DBs (sessions migrated, messages not yet) stay on the v0.7 path to avoid runtime "no such column" errors. When absent, model fields stay nil/0 and the views render placeholders. Older databases keep working; newer columns light up automatically once the database has them.

**Log line format.** Hermes log lines may carry an optional `[session_id]` tag between the level and the logger name. [`HermesLogService.parseLine`](Core-Services) treats the tag as an optional capture group, so older untagged lines still parse.

**ACP capability gates.** Rich Chat checks for `session/list` and `session/load` support; if Hermes doesn't advertise them, the session picker / reconnect UI degrades gracefully (you can still chat, just with reduced session navigation). Note that Scarf no longer sends `session/resume` at all — reconnects are load-only, because Hermes's resume silently creates an orphan server-side session when given an unknown id while a failed load is detectable and falls back to `session/new`.

**CLI output parsing.** Where Scarf parses `hermes` CLI output (Health, Tools, Pairing), the parsers tolerate field reordering and unknown lines.

**HERMES_OVERLAYS mirror.** [`ModelCatalogService.overlayOnlyProviders`](Core-Services) mirrors the overlay-only entries from `hermes-agent/hermes_cli/providers.py`. The set has grown across releases — the original v0.10 group (Nous Portal, OpenAI Codex, Qwen OAuth, Google Gemini CLI, GitHub Copilot ACP, Arcee), the v0.12 additions (GMI Cloud, Azure AI Foundry, LM Studio, MiniMax OAuth, Tencent TokenHub), the v0.14 additions (xAI OAuth, NovitaAI), and the v0.15 addition (OpenAI `openai-api`). When Hermes adds a new overlay-only provider, Scarf needs a release to surface it in the picker — but existing overlays silently pick up base-URL and auth-type refinements without a Scarf release, because only the identity is mirrored, not the full overlay struct.

**Device-code OAuth flow (v0.10.0+).** Nous Portal sign-in goes through `hermes auth add nous --no-browser` as a subprocess (see [`NousAuthFlow`](Core-Services)). Scarf regex-extracts the device-code block from stdout and auto-opens the verification URL via `NSWorkspace`. On success, it re-reads `~/.hermes/auth.json` to confirm `providers.nous.access_token` landed. Any change to Hermes's `To continue: / 1. Open: / 2. If prompted, enter code:` output shape would break the parser — low-risk because it's been stable across v0.9 and v0.10, but worth a smoke test on future Hermes releases.

**iOS exec channel — non-interactive PATH (v2.5+).** `CitadelServerTransport` runs commands over Citadel's raw exec channel which doesn't source the user's shell rc files, so non-interactive sessions land with a stripped PATH (typically `/usr/bin:/bin`). pipx installs `hermes` at `~/.local/bin/hermes`, and many sub-tools (git, curl, python) live in homebrew prefixes that the remote sshd would otherwise add via login-shell init. Mac's OpenSSH sshd handles this transparently; Citadel does not. v2.5 inline-prepends `PATH="$HOME/.local/bin:/opt/homebrew/bin:/usr/local/bin:$PATH"` on every iOS-routed `runProcess` so bare `hermes` resolves AND any subprocess it spawns can still find its tools. If you install `hermes` at an unusual path on a remote host (custom virtualenv, system-managed install dir), set the **Hermes binary hint** field when adding the server to point at the absolute path.

**iOS exec output capture (v2.5+).** Citadel's `executeCommand` API throws `CommandFailed` on any non-zero exit and *discards* the captured stdout buffer in the throw path. `hermes skills browse` happens to print its full table and *then* exit non-zero on some hosts — pre-2.5 iOS got nothing while Mac (Foundation `Process`) got the full table with `exitCode=1`. v2.5 drives `executeCommandStream` directly, drains stdout + stderr regardless of outcome, and recovers the exit code from the `CommandFailed` catch — feature parity with Mac for any Hermes command that emits useful output before exiting non-zero.

## v0.11 CLIs not yet adopted

Hermes v0.11 added a handful of new top-level CLIs Scarf doesn't yet drive directly: `hermes plugins`, `hermes webhook`, `hermes insights`, `hermes logs`, `hermes dashboard`, `hermes completion`. Scarf still reads the underlying files (`~/.hermes/plugins/`, `~/.hermes/webhooks/`, etc.) directly today, which keeps working. Switching to the canonical CLIs is forward-compatible work for v2.6+.

**`hermes memory reset`** is surfaced as the **Reset memory…** toolbar action on Memory views (Mac + iOS) with a destructive-confirmation dialog.

**`hermes profile`** is half-adopted as of v2.5.1. Scarf doesn't yet drive `hermes profile create / use / delete` from in-app UI (still file-based, still local for now), BUT Scarf v2.5.1+ **respects the active profile** by reading `~/.hermes/active_profile` at path-resolution time via [`HermesProfileResolver`](Core-Services). So `hermes profile use coder` on the host followed by a Scarf relaunch correctly reads `~/.hermes/profiles/coder/state.db`, `config.yaml`, sessions, memory, cron, etc. See [Projects & Profiles](Projects-and-Profiles) for the full profile model. In-app profile switching (writing `active_profile` from a UI control) is a separate v2.6+ feature — handling running ACP processes through a profile switch is more involved than just flipping a file.

## What breaks across major Hermes versions

If Hermes ships a major release that changes:

- **Database schema** — columns dropped, table renames — Scarf may need a release. Expected to be infrequent and called out in Hermes release notes.
- **ACP method names or message shapes** — chat would break. Scarf would ship an update with the new methods supported alongside the old.
- **CLI output format** — Health / Tools / Pairing would degrade. Often Scarf can ship a parser update independently.

When in doubt, check the [Health](Gateway-Cron-Health-Logs) view for compatibility warnings (Scarf surfaces the Hermes version it sees and flags mismatches with what it was tested against).

## Reporting a compatibility issue

If a new Hermes release breaks something in Scarf, please file an issue including:

- Output of `hermes --version`.
- Scarf version (Settings → General → About).
- The specific view that's broken and what's wrong.
- The relevant log snippet from `~/.hermes/logs/errors.log` (filter sensitive content first).
