Phase 4 of projects-first-class (branch feat/projects-first-class, t-eb8c7005, commit d21211a). `ProjectDoctorService` (ScarfCore) is one reconciliation pass over the registry index, each project's `<root>/.scarf/project.json`, the on-disk `.scarf/` scan and cron — 12 finding kinds, 4 repair kinds, surfaced in a doctor sheet + a cockpit health row + the P2 damage banner's new "Open Project Doctor" button. Deliberately does NOT read state.db: cron `workdir` is the only Hermes-side signal used, which keeps charter C3/C4 out of scope entirely and the pass fast. Checkpoints / `sessions.cwd` / kanban enumeration stay DEFERRED.

## Observations
- [constraint] Repairs are refused WHOLESALE while the registry decode lost whole ROWS or was quarantined — each repair ends in a registry rewrite, which would make that loss permanent (the P2 `registryForMutation` rule). Field-level salvage deliberately does NOT block: a dropped field held an invalid value and replacing it IS the repair. `repair(_:)` re-derives the block from ONE fresh `loadRegistryDetailed()` that also supplies the rows it writes back — reading twice left a window where the file could go lossy between the check and the write. #projects #dataloss
- [gotcha] A record that EXISTS but doesn't parse is never a `missingRecord`: `save(derive(...))` would overwrite the only copy. Same rule applies to the ORPHAN path — a candidate dir whose `project.json` is malformed is reported, not offered for adoption, because adoption derives a record and writes it. Both classifications are re-checked at repair time (`refuseIfRecordIsUnreadable`), since the file can change between the report and the button. #gotcha
- [gotcha] The orphan scan compares paths TEXTUALLY and `ProjectIdentity` never expands `~`, so tilde-rooted paths are skipped entirely: on SSH `defaultProjectsRoot` is the unexpanded `~/projects` while rows are `/home/<user>/…`, and comparing them would report EVERY listed remote project as an orphan (and adopting one would persist a second identity seeded on the tilde spelling). Also: the user's home is never a scan root, candidates are capped at 400 total, and `~/.hermes` + `~/.hermes/profiles/*` are excluded — but NOT the whole `~/.hermes` subtree, because a Hermes home can sit above a projects dir. #remote #gotcha
- [decision] Identity repairs are WITHHELD for a path more than one row claims: every writer underneath addresses a row by path and stops at the first match, so repairing one of two rows leaves the other and the finding never clears — a button that silently does nothing. `duplicatePath` is the finding that actually resolves it. Same reasoning for `recordIdMismatch` when the RECORD holds the path-derived id and the row holds a minted one: "the record wins" would demote an asserted identity to a derived one, so it is report-only. #projects #identity
- [gotcha] The doctor's report is REGISTRY-WIDE but the cockpit builds a new view model per project, so the verdict is cached per SERVER in `ProjectHealthCache` (5-minute window, invalidated when the doctor sheet closes) — an instance-scoped flag re-ran a full directory crawl on every sidebar click. The cockpit health row filters to findings concerning THAT project (`report.issues(forProjectPath:name:)`); a registry-wide count there blames one project for another's problem. #perf #remote

## R1 remediation (commit 7460cf9): the block is borrowed, and field damage became a finding

- [decision] The doctor no longer derives its own lossy rule. `repairBlock` is `ProjectDoctorRepairBlock(loaded.loss)` — a presentation wrapper over the app-wide `RegistryLoss` (it says "repairs" where the sidebar says "changes") — with a new `registryUnreadable(path:)` case for a zero-byte / unreadable registry. `repair(_:)`'s pre-check is now UX: `saveRegistry` refuses a lossy write from underneath every branch anyway, so the check exists to fail BEFORE a repair writes a record and dies on the registry half. #projects
- [decision] Field salvage still does not block, and is now REPORTED: `registryFieldSalvaged` (medium, report-only, one finding per row listing the fields). Nothing else in the app was ever going to mention a dropped `folder` / `archived` — unlike `uuid`, no second copy exists — and the next save writes the row without them. `uuid` is excluded from the finding only when `invalidRegistryUUID` was actually raised for that row: that finding is withheld for a duplicated path, so an unconditional exclusion reported the damage NOWHERE. #gotcha
- [gotcha] `repairBlockReason()` was dead code whose doc comment (and `ProjectStore.indexInRegistry`'s) cited it as the guard callers relied on. Deleted, not wired up: `repair(_:)` derives the block from its own single authoritative read on purpose, and a second read would reopen the window that read was written to close.
- [gotcha] Since a lossy registry now refuses writes everywhere, a swallowed `ProjectStore.save` (the `derive()` migration, FleetApply, the cockpit) can leave a `.scarf/project.json` with no registry row — which the doctor reports as a finding while its own repairs are blocked by the same damage. Self-amplifying noise on an already-broken registry; accepted, not addressed.


## R2 remediation: the doctor stopped believing agent-written files

Batch 2 of the fresh-eyes audit (t-1a1a9ce3). Every fix here is the same shape — a `project.json` or `projects.json` said something, and believing it damaged a project the user never asked about.

- [decision] **Adoption guards the name that will actually LAND.** `indexInRegistry` writes `record.name`, so a collision check on the folder BASENAME was checking a string the write never uses: an agent-written record naming itself after another project slipped straight past it, and the sidebar's name-keyed delete then removed both rows. Both `diagnose` (via `adoptionName`) and `repair` now guard `record.name`, falling back to the basename only when there is no usable record. #projects #identity
- [decision] **A record that declares a different `rootPath` is refused, not followed.** Every writer underneath addresses a project by `record.rootPath` — `save` writes `<rootPath>/.scarf/project.json`, `indexInRegistry` matches the row for `rootPath` — so a record at `/a/foo` claiming `/a/bar` made a repair of foo silently rewrite bar's record AND re-point bar's registry row. One hand-edited field. There is no safe reconciliation to guess at (which of the two is wrong?), so `ProjectDoctorError.recordPathMismatch(path:declared:)` reports it and writes nothing. Applies to adopt, reindex and writeMissingRecord alike. #dataloss #gotcha
- [gotcha] **Valid JSON is not a record.** `sidecarState` answers `.ok` for any parseable JSON, and every path that trusted `.ok` went on to `derive()` a record and write it — so a `project.json` holding `{"note": "wip"}` was replaced wholesale. `recordState` (same single read, `JSONDecoder().decode(ScarfProject.self)`) is now what gates adoption and `refuseIfRecordIsUnreadable`. The generic classifier still serves the report-only sidecars. #dataloss
- [decision] **`deadRootPath` is one finding per FOLDER, not per row**, keyed on the normalized path and carrying `affectedRowCount`. Removal matches rows by normalized path (converging with `ProjectStore.indexInRegistry`), so `/a/b` and `/a/b/` are one dead folder claimed twice; two findings meant a second button that could only ever throw `rowVanished`. The destructive confirm copy comes from the finding (`confirmTitle` / `confirmMessage`) rather than the sheet assuming one row. #ux
- [gotcha] The `allowEmpty: removed == before` on that save is behaviourally identical to the `true` it replaced — `saveRegistry` consults the flag only when the list is empty, which is exactly when that condition holds. Kept as the condition because the condition is what we can justify; the real protection against blanking a misread list is the upstream lossy-load refusal. Documented in the code so nobody re-derives it as a fix.
- [decision] **The `~`-home hole is closed structurally.** On SSH `paths.home` is the unexpanded `~/.hermes`, so the home exclusion and the `userHome` guard compared against a string no absolute path could equal — inert exactly where they mattered, and a row at `/home/alan/proj` turned `/home/alan` into a scan root (300 entries × 2 `fileExists`, over SSH, for one health check). With no expandable home we cannot NAME the home directory, so we decline to scan anything shallow enough to BE one: a scan root needs three absolute segments when the home is non-comparable. Extracted as the pure `ProjectDoctorService.scanRoots(rowPaths:home:defaultProjectsRoot:)` because the rule cannot be exercised through a local `ServerContext` — which is why it stayed broken. #remote #gotcha
