## Observations
- [sidebar] Kanban moved from Manage → Monitor in SidebarView (between .activity and remaining Monitor entries) — it's runtime WIP, not configuration #navigation
- [hermes-constraint] Hermes has NO `update` verb — priority/title/body/tenant are write-once on `kanban create`. Mutations are state transitions (assign/dispatch/complete/block/unblock/archive) or new comments — `claim` is deliberately NOT wrapped (P25; see `KanbanTransitionStep`'s doc: claiming flips status to `running` without spawning work, so the task gets reclaimed on stale_lock ~15 min later). Inline card-title editing is impossible at the wire level #constraints
- [hermes-constraint] Hermes Kanban is ONE global SQLite DB at ~/.hermes/kanban.db. It DOES have a `project_id TEXT` column (`hermes_cli/kanban_db.py:866-869` @ v2026.9.7) but it is unusable as a Scarf key: it links to a first-class Hermes Project in the creator's per-profile `projects.db`, and `create_task` SILENTLY DROPS an id that does not resolve there (`:1110-1117`, `:1124-1127`). Scarf keys on the free-text optional `tenant TEXT` instead: each project gets a `scarf:<slug>` tenant minted on first kanban interaction. P42 corrected the old "no project_id column" premise, which was false #constraints #tenants
- [hermes-constraint] No within-column position field — drag-to-reorder inside a column has no persistence path and is DISABLED. Sort key is `priority DESC, created_at DESC` (matches dispatcher run order). Cross-column drag is the only persisted gesture #constraints
- [hermes-constraint] No file-watch/webhooks — polling at 5s while foregrounded. Live `watch` streaming deferred; future hasKanbanWatch flag will gate #constraints
- [columns] Hermes status enum has 7 values; board collapses to 5 columns: Triage / Up Next (todo+ready) / Running / Blocked / Done. Triage hides when empty. v0.15 adds Scheduled + Review columns (collapsed when empty) #columns
- [v016-additions] v0.16.0 adds hasKanbanGoalMode gate for goal-mode tasks (separate kanban stack for goals vs. tasks, dedicated verb constraints, board filtering) #v0.16
- [service] KanbanService is a Sendable actor in ScarfCore — pure I/O, no UI state. Wraps the v0.12+ verbs Scarf actually drives — `claim`, `link`, `unlink` and `swarm` wrappers were DELETED in the round-2 audit (P25) as unreachable/wrong-verb surface. Each method dispatches via Task.detached(priority:.utility). Errors land in KanbanError → inline banners (not modal alerts). 'no matching tasks' stdout → [] #service
- [transitions] KanbanService.plan(for: KanbanTransition) is a pure function mapping (from, to) → verb sequence. e.g. (.upNext,.running)→[.dispatch], (.blocked,.running)→[.unblock,.dispatch]; `.scheduled` is a second source state for `unblock` alongside `.blocked`. Forbidden transitions throw KanbanError.forbiddenTransition with user-facing reasons (Done is terminal; Triage is specifier-promoted only) #transitions
- [tenant] KanbanTenantResolver (Mac) mints `scarf:<slug>` on first kanban interaction, persisting to <project>/.scarf/manifest.json via ProjectManifestStore (GW-E2c guarded writer). Tenants are IMMUTABLE across rename. Bare projects get a sentinel manifest (id: scarf/<project-id>, version: 0.0.0); ProjectAgentContextService refuses to surface sentinels as a Template line. Tenant reads throw on manifest-present-but-unreadable (GW-F2 safety) to prevent silent collision mints. Cross-platform reader: KanbanTenantReader in ScarfCore #tenants #guarded-write
- [agent-injection] ProjectAgentContextService.renderBlock adds 'Kanban tenant' line to AGENTS.md scarf-managed block when tenant exists. ChatViewModel.startACPSession calls refresh(for:) before opening every project chat — agent learns to pass --tenant scarf:<slug> on every create. Misuse falls through to global Untagged group, acceptable v2.7.5 behavior #agents
- [view-model] KanbanBoardViewModel (@MainActor + @Observable) holds column-grouped tasks. Optimistic-merge for drag-drops: in-flight move records optimisticOverrides[taskId]=newStatus, mutates local array immediately, clears only when poll confirms. Without this, a stale poll can clobber a card the user just dragged #concurrency
- [inspector] KanbanInspectorPane is a 420pt SIDE-PANE, not modal — so the user can keep dragging cards after inspecting one #ux
- [v015-additions] v0.15 adds: server-side --sort (priority/created/status/assignee/title/updated), promote/schedule/purge verbs (Hermes also has `swarm`; Scarf's wrapper for it was removed in P25 — no surface drove it), global --board <slug> plumbing, branchName/workflowTemplateId/currentStepKey/modelOverride task fields (model_override is show-only), worktree:<path> workspace variant, session-scoped board via ACP session_id (replaces tenant + time-window approximation) #v0.15
- [gating] Single flag HermesCapabilities.hasKanban (**>= 0.13.0** — re-floored in P55, 2026-09-13: `hermes_cli/kanban.py` does not exist at v2026.4.30 = 0.12.0 and `kanban` appears zero times in that tag's `commands.py`/`main.py`; the board arrives at v2026.5.7 = 0.13.0, `commands.py:163`) gates all 27 verbs together. hasKanbanV015 gates the v0.15 maturation wave. hasKanbanSessionFilter gates the chat-scoped board. hasKanbanGoalMode gates goal-mode tasks (v0.16+). Global Kanban sidebar + per-project Kanban tab stay on hasKanban (tenant-scoped) — only chat-scoped surface requires v0.15 #gating
- [iOS] Read-only board on iOS — ScarfGoKanbanView renders the 5 columns as a horizontally-paged Picker of single-column lists (HIG-friendly on iPhone). No mutations, no drag-drop in v2.7.5. Card titles use semantic .headline (not ScarfFont) so Dynamic Type works; chrome uses ScarfBadge for fixed visual weight #ios
- [anti-patterns] Don't add within-column reorder via client-side ordering sidecar — diverges from dispatcher run order. Don't try to mutate priority/title/body post-create (no verb). Don't drop cards from .done into anything (Done is terminal). Don't call transport.runProcess directly from view bodies — route through KanbanService so polling + writes share concurrency model #pitfalls

- [fact] Round-4 P42/P42b: `HermesKanbanTask` now decodes `project_id` and `provider_override`. `provider_override` is gated by `HermesCapabilities.hasKanbanProviderOverride = isV0191OrLater` — the key enters `_task_to_dict` at `v2026.7.30:80` (0.19.1) and `cmd_list` emits it from the same tag (`:1594`); P42's first floor of v0.21.1 was wrong because it grepped `_TASK_DICT_FIELDS`, the CONSTANT the task dict MOVED into at `v2026.9.7` (`hermes_cli/kanban.py` → `kanban_output.py`). `project_id` gets NO flag on purpose: it is decode-only and `decodeIfPresent`, so a pre-v0.18 row answers `nil` — the same answer an unlinked task gives — and a flag would gate nothing. #capability-gating #tenants


- [fact] **The Review column has TWO exits, and their floor is v0.20.1 — not `hasKanbanV015`** (P56, round-6 decision 6, `e4e25ccb`). `review -> done` is `kanban complete`: `complete_task`'s UPDATE reads `AND status IN ('running', 'ready', 'blocked', 'review')` at `hermes_cli/kanban_db.py:2572` @ `v2026.9.7`, and the THREE-status form (no `'review'`) at `v2026.8.3` (0.20.0) and at every tag below it, **including the v0.15 floor `v2026.5.28`**. `review -> upNext` is `kanban reopen-review` (`kanban_parser.py:323-326`, `kanban.py:990-1008`, `reopen_review_task` `kanban_db.py:3295-3328`), which moves the row to `_landing_status_after_parents` — `ready` or `todo`, both of which the board collapses into Up Next — and whose name occurs zero times under `hermes_cli/` through `v2026.8.3` and twice from `v2026.8.13`. One flag for both doors: `hasKanbanReviewExits = isV0201OrLater`. Before P56 every drag out of Review threw "No CLI path exists for this transition." on every host; below the floor that refusal stands and now names the version. `review -> blocked` stays refused at EVERY tag (`block_task` updates only `WHERE … AND status IN ('running', 'ready')`, `:2929`) and its refusal must NOT mention a version, since no upgrade fixes it. `KanbanService.plan(for:caps:)` takes `caps` with no default #transitions #capability-gating #v0.15
- [decision] **A drag that dispatches shows a confirmation naming the board-wide pass** (P56, round-6 decision 9). `hermes kanban dispatch` has NO per-task selector — `--dry-run` / `--max` / `--failure-limit` / `--json` is the whole argv (`hermes_cli/kanban_parser.py:346-353` @ `v2026.9.7`) — so dropping ONE card spawned workers for every assigned `ready` task in priority order and could start a different one first. `KanbanBoardViewModel.attemptMove` computes `plan` first (pure; see `KanbanService.plan`'s table), then checks `if !confirmed, plan.steps.contains(.dispatch)` and parks that as `pendingDispatch`, returning **before the optimistic override too**, so a cancelled drop leaves the card where the user picked it up with nothing to roll back; `confirmPendingDispatch()` is the only caller passing `confirmed: true`. The confirmation is keyed on the PLAN's computed steps, not the destination — the old destination-based check (`== .running`) was wrong in both directions: it asked on transitions the planner refused (Done/Review without exits/Triage/Archived → Running throw before dispatch), and missed future routes into Running that don't dispatch. `blocked` and `scheduled` sources both plan `[.unblock, .dispatch]` and the inspector's Claim button routes through the same `attemptMove` #ux #concurrency
- [fact] **`KanbanCreateRequest.branch` is gone** (P56). It emitted `--branch` ungated; the flag first exists at `v2026.5.28` (0.15.0) and `"--branch"` is absent from `hermes_cli/kanban.py` at `v2026.5.16` (0.14.0), where argparse would have exited 2 on the whole create — but no production caller ever set it, so deleting the parameter beat a new capability flag plus its four-test floor group guarding a field nothing fills. `KanbanModelsTests.createRequestArgvNeverCarriesBranch` is the alarm; the floor walk is recorded in the file so re-adding it WITH its gate costs nothing #capability-gating
- [gotcha] **`KanbanBoardViewModel.capabilities` is the whole `HermesCapabilities` struct, not another `supports…` Bool.** The planner takes the struct, a second gated arm would need a second mirror, and a mirror that can disagree with the store is the bug. `.empty` is the default so a Preview or an unresolved version probe keeps the pre-P56 refusal rather than offering a drag the host declines #gating
