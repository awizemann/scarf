P1 hardening pass (t-11fd245b) on @danmarauda's push-to-talk dictation feature (commit 51584c0c). The original code set `request.requiresOnDeviceRecognition = recognizer.supportsOnDeviceRecognition`, which silently fell back to Apple's server-assisted recognition on locales/devices without on-device support — contradicting `NSSpeechRecognitionUsageDescription`'s "on this device" promise. Fixed by refusing to record at all when on-device isn't available, with a defense-in-depth check inside the transcriber too. Dictation must keep this contract: on-device or nothing, never a silent server fallback. This matters because `NSSpeechRecognitionUsageDescription` promises "on this device" for dictation. The on-device promise is DICTATION's only, not the app's: Live Voice (P5b), started by the user after a one-time consent (F4, t-ba3ccc85), streams microphone audio DIRECTLY from the phone to OpenAI over WebRTC (the Hermes host only runs the session exchange, so OpenAI also sees the phone's IP) and seeds each session with up to 24 recent chat messages / 6,000 chars. `NSMicrophoneUsageDescription` says both (dictation transcribed on this device; Live Voice streams directly to OpenAI). The empty `NSPrivacyCollectedDataTypes` in `Scarf iOS/PrivacyInfo.xcprivacy` means the developer collects nothing; it is not a claim that no data leaves the device (the App Privacy label question for Live Voice is task t-11cc53ea). See "ScarfGo Live Voice (P5b)" and "Live Voice core".

## Observations

- [gotcha] `SequenceGesture<LongPressGesture, DragGesture>.Value`'s `.first` case fires at TOUCH-DOWN, before the long press succeeds — there is no separate `.first(true)` callback for success; the transition into `.second(true, _)` IS the success signal. `ChatView.dictationGesture` used to start a take on any `.first` (P1 audit t-0fbb1c3c, fixed on the voice-f1 branch), so recording began on every touch-down, and since SwiftUI never calls `.onEnded` for a gesture that failed to recognize, a quick tap or a VoiceOver double-tap (which fails the 0.2s long press) left the take running forever. Fix: gate `holdBegan()` on `.second(true, _)` only, inside `DictationGestureReducer` — a pure state machine factored out of the `Gesture` closures specifically so this is unit-testable (`DictationGestureReducerTests` in `Scarf iOSTests/`) without simulating a real touch
- [gotcha] The `SFSpeechRecognitionTask` `recognizer.recognitionTask(with:)` returns must be retained for the whole call — a bare local `SFSpeechRecognizer` plus a dropped task handle (the original `OnDeviceSpeechTranscriber.transcribe`) means nothing can cancel a take whose completion handler never fires, parking `PushToTalkController.phase` at `.transcribing` forever (disabling both dictation and Live Voice until relaunch). Fix: `RecognitionTaskHolder` retains recognizer+task and is driven by `withTaskCancellationHandler`, whose `onCancel` both calls `task.cancel()` AND force-resumes the continuation directly (`cancel()` isn't documented to guarantee the completion handler still fires) — plus `PushToTalkController.transcribe(with:url:timeout:)` races the whole call against a bounded `Duration` timeout (`transcriptionTimeout`, 20s in production) via `withThrowingTaskGroup`, so a hang is bounded even if the cancellation plumbing were ever incomplete. Covered end-to-end by `MockTranscriber.hangs` (a `Task.sleep` that itself honors cancellation, standing in for a well-behaved transcriber) plus an injectable short `transcriptionTimeout` in the test initializer</content>

- [invariant] Dictation must never fall back to server-side speech recognition — `OnDeviceDictationAvailabilityChecking.isOnDeviceRecognitionAvailable()` is checked in `PushToTalkController.startRecording()` BEFORE any recording starts, and `OnDeviceSpeechTranscriber.transcribe` sets `requiresOnDeviceRecognition = true` unconditionally (throwing `DictationError(reason: .onDeviceRecognitionUnsupported)` instead of relaxing it) as defense-in-depth
- [convention] Availability/permission checks for AVFoundation/Speech features go behind an injected `Sendable` protocol (`OnDeviceDictationAvailabilityChecking`, mirroring the existing `PushToTalkPermissionChecking`) so the composer state machine stays testable without a simulator's real mic/speech stack
- [gotcha] `AVAudioSession` interruptions (phone call, Siri) are NOT handled by `AVAudioRecorder` automatically from the app's state-machine perspective — without an explicit `AVAudioSession.interruptionNotification` observer, `PushToTalkController.phase` gets stuck at `.recording` after an interruption steals the session. Production wiring: a `Task` in `init()` consumes `NotificationCenter.default.notifications(named:)` (inherits MainActor isolation since it's a direct `Task {}` literal in a MainActor sync context) and calls an internal (not private, so `@testable` can drive it directly) `handleAudioSessionInterruption(began:)` — tests never post a real system notification
- [convention] A `@State`-owned controller class in a `TabView` tab (e.g. `pushToTalk` in `ChatView`) DOES get `.onDisappear` on a tab switch even though the class instance itself survives (SwiftUI keeps `@State` identity across the switch) — wire teardown (`handleViewDisappearing()`: cancel an in-flight recording like a drag-away-cancel, cancel an in-flight transcription Task and drop its result via `Task.isCancelled`) there, unlike ChatController's ACP session which deliberately stays alive across tab switches (see the `.onDisappear` comment in ChatView.swift) — audio capture and a network session have opposite correct behavior on tab-away
- [fact] `PushToTalkNotice.opensSystemSettings` gates a Settings deep-link button in the composer's notice strip — only true for `.microphonePermissionDenied` / `.speechPermissionDenied` (fixable from Settings); restricted/MDM and on-device-unsupported have no Settings toggle so the link is omitted rather than shown-but-useless
