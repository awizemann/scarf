## Observations
- [format] .scarftemplate is a zip containing: template.json (manifest with id/name/version/contents claim), README.md (preview), AGENTS.md (REQUIRED — cross-agent instructions standard used by Claude Code, Cursor, Codex, Aider, and 20+ other agents), dashboard.json, optional instructions/ (CLAUDE.md/GEMINI.md/.cursorrules/.github/copilot-instructions.md), optional skills/<name>/ (installed to ~/.hermes/skills/templates/<slug>/), optional cron/jobs.json (registered paused; since R12 named `[tmpl:<id>] [proj:<uuid>] <name>` — project uuid minted before cron create — because the template tag alone is shared by every install of one template; legacy `[tmpl:<id>] <name>` jobs still attribute by template id; one rule in ScarfCore `ProjectCronAttribution`), optional memory/append.md (added to MEMORY.md as its OWN Hermes memory entry — `\n§\n` delimiter, ENTRY_DELIMITER tools/memory_tool_store.py:23 @ v2026.9.24 — wrapped in `<!-- scarf-template:<key>:begin/end -->` markers where key = first 16 hex of SHA-256(template id) since R16a — the id-spelling markers were replaced by Hermes's html_comment_injection scan (tools/threat_patterns.py:31 @ v2026.9.24, memory_tool_store.py:132-146) for ids containing system/secret/hidden/override/ignore; legacy id-spelling markers are still detected/stripped via ProjectTemplateService.memoryBlockMarkers(in:templateId:)), optional slash-commands/<n>.md (manifest schemaVersion 3; installer accepts 1...3 since R12, matching tools/build-catalog.py) #format
- [services] ProjectTemplateService (inspect + validate + plan), ProjectTemplateInstaller (execute plan), ProjectTemplateExporter (build from project), ProjectTemplateUninstaller (reverse via lock file). UI in Features/Templates/. Deep links via TemplateURLRouter + scarfApp.swift onOpenURL #services
- [deep-link] scarf://install?url=<https URL> and file:// URLs for .scarftemplate files trigger install flow #url-scheme
- [lock-file] <project>/.scarf/template.lock.json is written after every install and drives uninstall. Only files in lock.projectFiles are removed — user-added files (e.g. sites.txt) preserved. If every file in dir was template-installed, dir is removed; otherwise dir stays. Skills namespace removed wholesale (isolated). Cron jobs removed via `hermes cron remove <id>`; since R12 a non-zero exit, an unreadable jobs.json (names go to `cronJobsUnverified`, never "already gone") or a name shared by several live jobs (resolved by prompt/workdir naming this project, else reported) comes back in `TemplateUninstallOutcome.leftovers` and the success sheet says "Removed, except:". Memory: the marker-bounded entry is removed together with its own `\n§\n` delimiter so neighbouring entries come back byte-identical; legacy blank-line-glued blocks still stripped the old way #uninstall
- [export] ProjectTemplateExporter reads everything through the transport, including `.scarf/manifest.json` for the forwarded config schema (R12: it used FileManager, so remote exports silently lost the schema), and copies each skill's whole tree (references/, scripts/, …; dotfiles and .bak/.corrupt- guard artifacts skipped, symlinks followed only while their host-resolved target (realpath / readlink -f via transport) stays inside the skill folder's own resolved path — since R16a a link leading outside (e.g. to ~/.hermes/.env) or unresolvable REFUSES the export (ProjectTemplateError.unsafeSkillLink); dangling links skipped; depth 12) #export
- [security-design] Templates can only write file types declared in manifest (README, AGENTS, dashboard, instructions/, skills/, slash-commands/, memory/append.md, optional config). buildPlan creates TemplateFileCopy only for these types, preventing writes to config.yaml, auth.json, sessions, or credential paths via architectural guarantee (not explicit refusal check). Preview sheet is load-bearing: user's only trust boundary is that the sheet is honest about everything about to be written #security
- [remote] Remote (SSH) installs are real and default to `~`-rooted paths (`~/projects/<slug>`, `~/.hermes/…`). `PathGuard` and `ProjectRootPolicy` only accept absolute paths, so until B03 (blind re-audit S12-F1) every remote uninstall was root-refused. The uninstaller now expands `~` against the probed home (`resolvingUserHome()` → `ServerContext.resolvedUserHome`, via the shared `ServerContext.expandingTilde`) BEFORE the unchanged strict checks; for SSH the root policy is given the probed home + expanded Hermes home so a `~` / `~/.hermes` row is refused. An unresolved home → refused plan with the reason; nothing removed. Keychain binding still uses the UNEXPANDED `project.path` (the spelling the installer hashed). The installer now expands a `~` parent to the absolute remote path, so new rows, locks, cron workdirs and `{{PROJECT_DIR}}` are absolute. The outcome names every file/refused entry/skills folder/project folder left behind; `projectDirRemoved` is what the run removed, never a post-hoc `fileExists` (false on a dropped SSH link). Dashboard file widgets on such rows: `CockpitDashboardPanel` resolves the root off-main with `WidgetPathResolver.resolveRoot` (probed host home, never the Mac's) and passes `WidgetHostHomes` so the widget root policy refuses `~`/`~/.hermes` rows; a still-`~` root is refused as `.unresolvedHome` #uninstall #remote
- [no-undo] No 'undo' for uninstall — destructive. Re-install means running install flow again #semantics
- [invariant] Cron job skill refs (R18a, T8-F1): the exporter writes a shipped skill (exact skill id in the export plan) by its bare bundle name; the installer rewrites a bare shipped name, or a `category/name` whose name is shipped and which does NOT resolve on the install host (`<skills>/<ref>/SKILL.md`), to `templates/<slug>/<name>` — the exact path, since Hermes resolves a ref as a direct path or a whole-string name and refuses a name two skills share (`tools/skills_tool.py:345-361` @ v2026.9.24). Refs that resolve (hub / Hermes-bundled skills) are kept #cron
