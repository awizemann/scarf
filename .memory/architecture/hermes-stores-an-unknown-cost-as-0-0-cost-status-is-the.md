Found validating t-b10d9fa6 against Hermes tag v2026.9.21 (v0.21.4) and the live `~/.hermes/state.db`; FIXED in t-fc311bef on branch `fix/unknown-session-cost` (2026-09-21), and CORRECTED in t-ba08805b on branch `fix/nil-cost-status` (2026-09-21) — the first pass got the `'unknown'` status right but mis-read a NULL `cost_status` as proof of an old host. Read the `[invariant]` on the column-vs-value discriminator before touching this rule.

Hermes's `cost_status` value set is declared exhaustively as `CostStatus = Literal["actual", "estimated", "included", "unknown"]` (`agent/usage_pricing.py:48` @ v2026.9.21). Three are produced in that file: `"unknown"` (`:550`, `amount_usd=None`, label "n/a"), `"included"` (`:565`, a true zero on a `subscription_included` route) and `"estimated"` (`:596`); `"actual"` is declared for a provider-reported cost.

Both persist paths collapse an unknown `amount_usd=None` to `0.0`: the `UPDATE sessions` statement built at `hermes_state_usage.py:29` (`estimated_cost_usd = COALESCE(?, 0)`, with `cost_status = COALESCE(?, cost_status)` at `:37`, executed by `update_token_counts` at `:275`), and the `session_model_usage` upsert at `:367` (`float(estimated_cost_usd or 0.0)`). So the stored number is identical for "don't know" and "genuinely free" — `cost_status` is the only discriminator.

Live evidence: every recent `source='acp'` session has real token counts with `estimated_cost_usd = 0.0` and `cost_status = 'unknown'` — the `:free` models have no pricing entry. Not ACP-specific; CLI and cron rows hit it too.

## Observations
- [fact] `SessionCostDisplay` (ScarfCore `Models/SessionCostDisplay.swift`) is THE one cost-presentation rule: `init(actualCostUSD:estimatedCostUSD:costStatus:)` returns `.amount(Double, isActual:)` / `.includedFree` / `.unknown` / `.legacy(amount:isActual:)`. Reach it via `HermesSession.costDisplay`; never re-derive a rule from the raw columns #cost
- [invariant] `.legacy` is the C1 escape hatch — an ABSENT `cost_status` COLUMN, or an unrecognised future status, with no positive amount carries the SAME raw `(displayCostUSD, costIsActual)` the surfaces read before, so an older host renders byte-identically. Note "column absent", NOT "value nil": a NULL value on a host that HAS the column is `.unknown` (see the correction below). ONE exception to "the same raw values", added in t-e84e6e1c: a NaN, infinite or NEGATIVE figure is dropped by `usableAmount` before any arm runs, so `.legacy` carries `amount: nil` rather than the corrupt number. `NaN > 0` is false, so such a value used to skip `.amount` and reach the surfaces through `.legacy`, printing "NaN"/"-$5.00" in a currency label; Hermes can only store a finite non-negative figure, so this is corrupt data, not a host-version difference. A corrupt ACTUAL still falls through to a usable ESTIMATE (tests: `corruptAmountsAreNotRendered`, `corruptActualFallsThroughToTheEstimate`).
- [invariant] **The discriminator is the COLUMN's existence, never the value's nullity.** `costStatus` decodes to nil in two opposite situations and Scarf must tell them apart: (a) the host is below the v0.7 schema so the `cost_status` column does not exist → `.legacy`, byte-identical to the prior release (C1); (b) the column EXISTS and Hermes left it NULL → `.unknown`, the em dash. `HermesSession.hasCostStatusColumn` carries (a) vs (b): a `Bool` defaulting to `false` (the conservative reading, so every fixture and hand-built session keeps the legacy behaviour), stamped from the probed `hasV07Schema` at the ONE place a session is built from a DB row — `HermesDataService.sessionFromRow` — which serves BOTH the local and the remote/SSH backend, since they share `Row` and that parser. `hasV07Schema` gates the SELECT that adds `cost_status` (`HermesDataService.swift:160-162`), so it is exactly "the column was in the SELECT". ScarfGo/iOS builds no `HermesSession` and has no session-cost surface. Fixed in t-ba08805b on `fix/nil-cost-status` (2026-09-21) #cost #capability-gating
- [gotcha] Why (b) is common, not exotic: `hermes_state_usage.py:37` writes `cost_status = COALESCE(?, cost_status)` only from `update_token_counts` (`:275` — **not** `:274`, which is blank at v2026.9.21), so any session that never completed a priced turn keeps `cost_status` NULL on a CURRENT host. Live v0.21.3 `~/.hermes/state.db` (2026-09-21): 9 of 43 sessions — 6 acp, 2 cron, 1 telegram, one of them 133 messages — all with `estimated_cost_usd` NULL too; `sessionListPredicate` (`HermesDataService.swift:249`) does not filter them out. Before the fix they took `.legacy(amount: nil)` and rendered a false `"$0.00"` in `SessionsView.costLabel` while `SessionInfoBar`/`SessionDetailView` rendered nothing at all for the same row — two surfaces disagreeing about one session. The original P6 fix asserted the opposite ("a nil `cost_status` means a pre-v0.7 host") in six comment sites; all six are corrected #gotcha
- [gotcha] Two tests pin the pair and neither is sufficient alone: `SessionCostDisplayTests.nilStatusIsByteIdenticalToBefore` (column ABSENT → never a new presentation, C1) and `nullStatusOnAModernHostIsUnknown` + `theColumnIsTheDiscriminator` (column PRESENT + NULL → `.unknown`). The first was the trap — it correctly pinned C1 for a pre-v0.7 host, and the P6 fix mistook that constraint for a statement about all nil statuses. `InsightsAggregatesTests` covers `unknownCostSessionCount`, which had no test at all. Mutation-checked: routing NULL-on-v0.7 back to `.legacy` fails 5 tests across the two suites #testing
- [constraint] An unrecognised FUTURE `cost_status` still degrades to `.legacy` even on a v0.7+ host — only NULL means "never priced". That leaves the unlocalized `"$0.00"` reachable on a current host for a status Hermes has not invented yet; deliberate, since inventing a rendering for an unknown word is the failure mode C1 exists to prevent. The `"$0.00"` literal in `.legacy` stays unlocalized on purpose (audit F9): it is byte-identical to the pre-fix `SessionsView.costLabel` #display-fidelity
- [decision] A POSITIVE amount always wins over the status word, because Hermes only ever stores the placeholder ZERO for unknown — never a positive one. `'unknown'` + non-positive → `.unknown` → the em dash `"—"`, never `$0.00`; `'included'` → a genuine zero rendered WITHOUT the " est." marker #cost
- [fact] Consuming surfaces: `SessionsView.costLabel`/`costCell`, `SessionInfoBar`, `SessionDetailView`, and `InsightsView.totalCostCard` (which shows `"—"` when the sum is 0 with unknowns, and a "partial" tooltip whenever `InsightsViewModel.unknownCostSessionCount > 0`). Three Dashboard sites were deliberately left alone — they already render only when the figure is `> 0`, so they never assert a false zero #display-fidelity
- [gotcha] The em dash needs an accessibility label or VoiceOver says "cost —". Keys added to `Localizable.xcstrings` + `tools/translations/*.json` for all six locales: `cost unknown`, `Hermes recorded no cost for this session`, `Partial — Hermes recorded no cost for ^[%lld session](inflect: true)` #i18n #a11y
