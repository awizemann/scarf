## Observations
- [pattern] Every release-gated UI surface in Scarf is feature-flagged via `HermesCapabilities` (scarf/Packages/ScarfCore/Sources/ScarfCore/Services/HermesCapabilities.swift). Detected once per server connection from `hermes --version` (semver + YYYY.M.D parse). #pattern
- [pattern] `HermesCapabilitiesStore` is injected on `ContextBoundRoot` (Mac) and `ScarfGoTabRoot` (iOS) via `.environment(_:)` and `.hermesCapabilities(_:)`. Gated UI reads it through the typed environment key. #dependency-injection
- [convention] Capability flags grouped by Hermes release with MARK comments: `MARK: v0.14 (v2026.5.16) flags`, `MARK: v0.15 (v2026.5.28) flags`, etc. Add a new flag whenever Scarf gains a release-gated UI surface. #convention
- [policy] Pre-target hosts gracefully hide new affordances rather than throwing on unknown CLI subcommands. Pre-v0.15 (and pre-v0.14) hosts must render byte-identical to the previous Scarf release. #compatibility
- [policy] Before implementing a new gate, verify exact flag/config/wire shapes against the corresponding Hermes source tag (e.g., `v2026.5.28`). #verification

- [gotcha] Verify a new flag's floor against EVERY intervening tag, not just the previous target. For the v0.21.0 cycle the audit scoped 0.20.5 → 0.21.0, but the intermediate v2026.8.27 (0.20.6) tag already shipped four surfaces the v0.21 release notes advertise — `cron incidents`, `cron resume --run-now/--at`, `--deliver bot-chat`, and the top-level `browser` subcommand — so they gate on a patch-level `isV0206OrLater`, not `isV021OrLater`. Only `peer run/status/stop`, `cron doctor`, and config dotted-key escaping (commit a42aee9585) are genuinely v0.21.0. Check with `git -C ~/.hermes/hermes-agent show <tag>:<file>` plus `git tag --contains <commit>`. #hermes #capabilities


- [gotcha] A capability flag can need an UPPER bound. A patch tag can RE-ADD a surface an earlier release removed — `plugins/web/tavily/` was deleted at v2026.8.31 (0.21.0) and restored at v2026.9.7 (0.21.1) — so a removal modelled as `!isV021OrLater` hides a live backend on every later host. Model a removal as a WINDOW (`semver == 0.21.0`), and only collapse it back to a floor once a later tag confirms the surface stayed gone. #hermes #capabilities
- [gotcha] "Absent at the old tag" must be established by walking the SYMBOL across every tag over every file location it has ever had, never by `git show <old-tag>:<new-path>`. The v0.21.1 modularization moved most argparse blocks out of `hermes_cli/main.py` into `hermes_cli/subcommands/<verb>.py`, so the old-tag path lookup fails and reads as "absent" — that alone mis-floored four surfaces (`skills search --json` is v0.17, `browse-sh` v0.15, `debug share -y` and `computer-use permissions status --json` v0.18). Use `git log -S<needle> --oneline -- <old path> <new path>` plus `git tag --contains <commit>`. #hermes #capabilities #verification


- [gotcha] **A tag walk means OPENING the file at each tag.** `git log -S<identifier>` / a grep across tags proves only when that IDENTIFIER was born — not when the BEHAVIOUR arrived, not that the surrounding arm still does the same thing, and not that a rename did not carry it in under another spelling. Round-4 P39–P44 re-opened every cited blob (`git -C ~/.hermes/hermes-agent show <tag>:<path>`) for every line number touched; a sweep that only adds a path prefix to an old citation is not a walk. #hermes #capabilities #verification


- [gotcha] **A flag whose surface exists at the supported minimum is not a capability — it is a bug with a version number.** P49 (round-5 decisions 9/10) retired `hasACPSetSessionModel`: `set_session_model` is in `acp_adapter/server.py` at `:466` @ v2026.3.17 (0.3.0, the earliest tag with an adapter), `:482` @ **v2026.3.30 = 0.6.0** — Scarf's supported minimum, with a working body — and `:929` @ v2026.9.7, so its "v0.13+" floor hid the chat model chip, the project model binding, the Models sidebar entry, the Chat Settings menu item and the iOS model badge from every 0.6.0–0.12 host that has the RPC. Unfloored, like `reset`/`context`/`version`. The P15/P23 rule ("a floor below the supported minimum is no floor at all") applies to ACP METHODS as much as to CLI verbs, and the tell is the same: the doc comment asserts a release, not a tag #capability-gating #verification
- [gotcha] **The MARK group's name is still not evidence — P49's light re-walk found two more.** Twenty flags were sampled across thirteen groups (two per group, opened at the floor tag and the tag before). Eighteen were correct; both failures sat in the v0.16 group and both were consumer-free: `hermes insights` is `hermes_cli/main.py:4634` (registered `:4627`, verb list `:3291`) at **v2026.3.30 = 0.6.0**, i.e. below the supported minimum, so `hasInsightsCommand` was deleted; `hermes dashboard` is `hermes_cli/main.py:4458` at **v2026.4.13 = 0.9.0** (registered `:4180`, `:5978`) and the string is absent from that file at v2026.4.8 = 0.8.0, so `hasDashboardCommand` re-floored 0.16 → 0.9. Both had sat wrong since the v0.16 cycle because nothing read them — **an unread flag is where a wrong floor survives longest**, so a re-walk should sample the consumer-free ones deliberately #capability-gating #verification
- [fact] **`hasContextCompressionCount` gates a field Hermes has never put on the ACP wire.** The adapter builds `Usage` from five keys at every tag — `prompt_tokens`, `completion_tokens`, `total_tokens`, `reasoning_tokens`, `cached_tokens`/`cache_read_tokens` — `acp_adapter/server.py:325-336` @ v2026.3.30 (0.6.0), `:1050-1059` @ v2026.5.7 (0.13.0, the claimed floor), `:917-924` @ v2026.9.7. P49 kept the flag and `ACPClient`'s tolerant camelCase/snake_case decode as a landing pad (the chip's `> 0` test means a never-sent field renders nothing) but rewrote the `TODO(WS-8-Q1)` and both doc comments to state the fact. **A tolerant decode is not evidence a field exists** #capability-gating #verification


- [gotcha] **A tag walk counts CALL SITES, not symbols — and a window can have a CEILING.** P51 (round-5, `c838c562`): `discord.allow_any_attachment` reads as a v0.15 feature and is one, but the Discord adapter stopped CALLING `_discord_allow_any_attachment` at `v2026.7.1` (0.18.0) while the getter LINGERED to `v2026.8.31`, and only at `v2026.9.7` is the getter gone and the key a documented no-op (`hermes_cli/config_defaults.py:1448`; `website/docs/user-guide/messaging/discord.md:703`). Grepping the SYMBOL would have put the window's end three releases late. Tag-by-tag call count: v2026.5.16 absent, v2026.5.28/5.29/6.5/6.19 → 2, v2026.7.1 → 0, and 0 through v2026.9.7 — so `hasDiscordAllowAnyAttachment` is `atLeastSemver(0,15,0) && !atLeastSemver(0,18,0)`, the first flag in the file whose UPPER bound is load-bearing. Gated rather than retired, on C1: a v0.15–v0.17 host honours the key and must still render the row #capability-gating #verification


- [gotcha] **A doc that cites a RELEASE is a doc nobody walked — and the release note may describe a feature that was reverted inside its own cycle.** P55 (round-6): `hasKanban` sat on `atLeastSemver(0, 12, 0)` because `RELEASE_v0.12.0.md` announced the board; the v0.12 TAG has no board at all. `hermes_cli/kanban.py` does not exist at **v2026.4.30** (pyproject = 0.12.0) and the string `kanban` appears ZERO times in that tag's `hermes_cli/commands.py` and `hermes_cli/main.py`; it all arrives at **v2026.5.7** = 0.13.0 (`commands.py:163`, `main.py:5278`/`:9232-9237`). Five consumers across three targets lit up on a 0.12 host and every `hermes kanban …` argv was an unknown verb routed to the agent at exit 0 — C5's four-dead-features class, with the board reading *empty* instead of *unsupported*. Re-floored 0.13 #capability-gating #verification
- [gotcha] **Half a per-flag verification is still an un-walked floor.** `hasBotChatCreationCLI` carried an exemplary doc: five flags of the create argv, each cited at the `hasBotMode` floor tag. The sixth line — "`--query-file` … first appears at v0.21" — was the only one with no tag walk behind it, and it was wrong: the flag is `hermes_cli/_parser.py:308` at **v2026.8.19 = 0.20.5**, absent at v2026.8.18. A floor set by the LAST flag to arrive is only as verified as that flag's own walk. Same round: `hasMCPIdentityHeader`'s 0.20.4 floor was three patches high (`identity_header`, `strict_redirect_headers` and the stdio `cwd` all land together in `tools/mcp_tool.py` at **v2026.8.13 = 0.20.1**, all absent at v2026.8.3) #capability-gating #verification
- [convention] **An ACCEPTED floor states what it costs.** Round-6 decision 5 kept `hasGatewayAllowlists` at v0.13 rather than splitting it per platform, and the doc now carries the walk that prices the decision: at **v2026.4.30** (0.12.0) `gateway/config.py` reads exactly ONE allowlist — Discord's `allowed_channels` at `:770-771` — while Telegram there has only `group_allowed_chats`, and the whole family (Slack, Telegram `allowed_chats`, DingTalk, Mattermost, Matrix `allowed_rooms`) arrives at v2026.5.7. The round-6 report had named two keys; the walk found one. Price an accepted gap by opening the file, not by trusting the finding that proposed it #capability-gating


## Round-6 P56/P56b — a flag's MARK group, and a decision that names a flag

- [gotcha] **A product decision that NAMES a capability flag is a hypothesis, not a citation — walk it like any other floor.** Round-6 decision 6 said the Kanban Review exits sit behind `hasKanbanV015`; the source says **v0.20.1**, five releases later, and the gap is exactly the range where the UI would have offered a gesture the host refuses. `complete_task`'s UPDATE admits `review` only from `v2026.8.13` (0.20.1) and `reopen-review` lands at the same tag, so the gate is the new `hasKanbanReviewExits = isV0201OrLater` (`HermesCapabilities.swift:1448`, `e4e25ccb`). C2 binds the phase agent even when Alan's decision already named a flag: open the file at the floor tag AND the tag before, then gate #capability-gating #verification
- [convention] **A flag's `// MARK:` group is a floor claim too, and every group-enumerating test is a membership contract.** `hasKanbanReviewExits` was filed under `// MARK: v0.20.4` at a 0.20.1 floor — the right home (that header already says the MARK is a LOCATION, never evidence, and since P55 no member carries a v0.20.4 floor), but the five group-enumerating tests in `HermesCapabilitiesTests.swift` never named the new member, leaving its floor unproven at every boundary the group already guards. P56b (`6a641ee8`) added it to all five with 0.20.1 polarity: ON at 0.20.3/0.20.4/0.20.5/0.21.0, OFF at 0.20.0. Either the header states the group is a location and each member carries its own verified tag (the shape here), or the header names a floor every member honours — either way the enumerating tests must list EVERY member #capability-gating #testing


- [gotcha] **In zsh, a tag-walk loop must brace the tag: `git show "${t}:tools/tts_tool.py"`, never `$t:tools/…`.** zsh parses `$t:t` as the `:t` (tail) history modifier, so the unbraced form silently asks for the wrong object, `2>/dev/null` hides the error, and EVERY tag reads as "symbol absent" — a floor that would land above the newest tag. Seen in the P2 voice walk (2026-09-18); the agent shell here is zsh. Sanity-check a walk by confirming the symbol IS found at the newest tag #hermes #capabilities #verification
