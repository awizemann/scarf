Manage Servers → Back Up / Restore (`.scarfbackup`), reworked in R05 (S14-F1/F2/F3 plus orchestrator follow-ups) after the backup ran `PRAGMA wal_checkpoint(TRUNCATE)` on the live state.db (a C3 write), tarred every other database live, and restore tarred over live databases. Scripts live in `HermesDatabaseScripts.swift` (shared by both sides).

## Observations
- [invariant] Backup never copies a live `*.db` and never checkpoints. EVERY `*.db` in the home (a symlink to a file included; retired-WAL captures `*.retired-wal-*` and excluded logs/mcp-tokens trees skipped) is snapshotted by `scarf_snap`: `sqlite3 -readonly VACUUM INTO` → `-readonly .backup` → `.backup` on a `PRAGMA query_only=1` connection ONLY after `sqlite3 :memory: '.dbconfig no_ckpt_on_close on'` echoes ON → python3 `mode=ro` backup() (not on macOS: CLT shim). Snapshots ship as `hermes-databases.tar.gz` at home-relative paths; manifest schema 2 `databases {entries, skipped}`; the home tarball excludes each database by exact glob-escaped path (a `*.db` pattern would swallow a directory named x.db) plus all sidecars. A root state.db that exists but isn't snapshotted fails the backup; other failures are listed as skipped, as `hermes backup` reports them #charter-c3
- [gotcha] Apple's /usr/bin/sqlite3 (and libsqlite3) cannot open a WAL-mode db read-only when its -wal and -shm are gone (a stopped Hermes): 'unable to open database file'. Homebrew sqlite3 and python's sqlite 3.53 can. That is why the query_only + no_ckpt_on_close rung exists. /bin/bash on macOS is 3.2: the scripts use only 3.2-safe features #sqlite
- [invariant] Restore refuses before any write while any process holds ANY database it will replace (always incl. state.db) or its -wal/-shm: Linux matches /proc fd links by target (`find -lname` with glob-escaped targets, `readlink` per fd where find lacks -lname; never `ls -l` parsing), `lsof -t` elsewhere, fails closed if neither; symlinked dbs resolved to their real path; Scarf's own pid excluded for the local server. Home extracted with databases/sidecars/retired-WAL captures excluded; databases (v2 snapshots, or v1 members lifted on the Mac with any archived WAL folded into Scarf's scratch copy) staged in the home (`tar -xm`) and published by `mv` after a re-check, `[ -f staged ]`, `chmod 600`, `rm -f` old sidecars, in one shell (mirrors hermes_cli/backup.py:536-559 @ v2026.9.24). Manifest database paths must be plain home-relative `*.db` paths #restore
- [decision] Replacing Hermes's databases during a user-initiated Server Restore is an APPROVED exception to charter C3 (Alan, charter task t-b4cfc798), pending the charter edit; it is only done with no holder present.
- [gotcha] The read-only snapshot may leave behind 0-byte `-wal`/`-shm` sidecars next to a cleanly-stopped WAL-mode database — this is exactly what Hermes's own `backup()` does too (verified on Debian/Ubuntu/Alpine) and is not a Scarf bug. It is not a content write: the sidecars carry no WAL frames, so it does not violate charter C3.
- [invariant] Restore targets the configured Hermes home (`--strip-components=1`); cron jobs are paused right after the home extract. Leftover `.scarf-backup-snapshot-*` / `.scarf-restore-staging-*` dirs at the home root are swept at the start of each run once untouched for a day #restore
- [invariant] Backup scope mirrors `hermes backup` (R18a, `hermes_cli/backup.py:46-118` @ v2026.9.24): `_EXCLUDED_DIRS` (backups, state-snapshots, checkpoints, browser-profile(s) — a browser credential store, always out — venvs, node_modules, .git, caches) at any depth; `hermes-agent` at the ROOT only; models/runtimes/node/browser_profiles and `cache/*` except images/audio/videos/documents/screenshots/citations at the root and each `profiles/<name>/` by EXACT name (GNU tar and bsdtar let `*` cross `/`, so `profiles/*/models` would drop a skill's own models/); pid/lock files, *.pyc/*.pyo, state.db.pre-update-emergency-*. The snapshot find prunes the same trees. Restore excludes them too (older archives) plus `_IMPORT_SKIP_NAMES` #backup
- [invariant] R19: the home tarball is created from INSIDE the home (`tar -C <home> .`, members `./…`, manifest `hermes.memberRoot = "."`). Tar matches exclude patterns UNANCHORED (GNU/BusyBox after any `/`, bsdtar at any path element), so the old `<leaf>/models` also dropped `<leaf>/skills/x/<leaf>/models/…` whenever the home's name recurred (Docker home `/opt/data`) — silent data loss. `./models` can't recur on GNU/BusyBox; bsdtar (libarchive pathmatch) skips a leading `./`, so a `tar --version | grep bsdtar` probe sets `$scarf_a='^'` (libarchive's start anchor) in front of every `./` pattern (`RemoteBackupService.homeTarCommand`/`anchoredExcludes`, same for the restore extract). Restore re-roots an older `<leaf>/…` tarball on the Mac with `bsdtar -s '|^leaf/|./|S' @old` (headers kept, hardlink targets rewritten, symlink targets not) before extracting. Verified GNU 1.26/1.29/1.35, BusyBox, bsdtar 3.5.3 #backup #tar
- [invariant] R19: Restore skips databases an older archive lists inside trees `hermes backup` leaves out (`RemoteBackupService.isInTreeHermesBackupLeavesOut`, mirrors `_should_exclude`/`_in_excluded_root_dir` tree rules, checked against the v2026.9.24 venv): not probed, not published, named on the done sheet (`RestoreResult.databasesSkipped`) #restore
- [gotcha] A pre-R19 Scarf restoring an R19 archive ignores `memberRoot`; its `<leaf>/` extract patterns never match `./` members, so only create-time excludes hold — `processes.json`/`gateway.lock` (import-skip names excluded only at extract) would be planted. Accepted #restore
- [gotcha] Any-depth tar patterns are `leaf/x`, `leaf/*/x`, … (8 depths), never a bare `x`: every tar also tests the archive's own top directory (a home named `backups` archived nothing), BusyBox's `*` never crosses `/` on create, and BusyBox EXTRACT excludes are start-anchored with prefix truncation (`find_list_entry2`), so the old bare `*.db-wal` never matched on alpine. GNU tar exits 1 on "file changed as we read it" (a live gateway rewrites gateway_state.json every minute): tar stages map GNU's 1 to 0 via `tar --version | grep 'GNU tar'`; bsdtar/BusyBox 1 is a real error and still fails. Verified in debian (GNU 1.35) and alpine (BusyBox 1.37) containers #tar
- [todo] Not handled: v1 archives' `*.db-journal` (torn mid-transaction copies, same as Hermes); holders owned by another user are invisible without root (same as Hermes) #follow-up
