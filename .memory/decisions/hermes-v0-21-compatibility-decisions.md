Forced config-parity decisions for the v0.21.0 ("Pantheon", v2026.8.31) cycle, work package W1. Tag map: v2026.8.19 = 0.20.5, v2026.8.27 = 0.20.6, v2026.8.31 = 0.21.0.

The recurring shape this cycle: the v0.21 release notes advertise changes that actually shipped in the intermediate v0.20.6 tag. W0 hit this on four capability flags; W1 hit it again on two of six config items. Deciding the floor by grepping only the newest tag would have mis-gated both.

Removal flags use INVERSE semantics (`true` = still show it) and differ deliberately in their unknown-version policy: a whole sub-editor (`hasWebExtractAux`) hides on unknown, matching `hasFlushMemoriesAux`; one entry in a picker (`hasTavilyWebBackend`) is kept on unknown, because hiding a list entry the user's config currently selects strands them on an invisible selection.

## W3 (curator pin/unpin, essential skill, roster reorg) — 2026-09-01

- [fact] `curator pin/unpin` diagnostic behavior — floor v0.20.6, not v0.21, despite being audited under the v0.21 umbrella. `hermes_cli/curator.py` `_cmd_pin`/`_cmd_unpin` (commits 7caa731e80, dd20c30dec) are present at v2026.8.27, absent at v2026.8.19. An ineligible pin/unpin exits 1 with the reason on stdout — `CuratorService.ensureSuccess` already surfaces this generically (falls back to stdout when stderr is empty) regardless of version, so no gating was needed there. An eligible-but-unmanaged pin/unpin exits 0 with a "this skill is unmanaged — run `curator adopt`" note that used to be silently discarded on the success path; `CuratorService.pin()`/`unpin()` now return that note (`String?`) instead of `Void`, detected by stdout content ("unmanaged" substring) rather than a capability flag — pre-v0.20.6 hosts never print the note on success, so the check is a natural no-op there.
- [fact] A skill that is both pinned and unmanaged legitimately appears in three independent places in `curator status` output at once (v0.20.6+, same 7caa731e80 commit): the managed `active`/`stale`/`archived` bucket totals, the `pinned (…)` names line, and the `unmanaged (…)` summary count. This is intentional upstream behavior (`curated_report()` adds pinned-but-unmanaged skills to its rows), not a double-count bug — `HermesCuratorStatusParser` already parses the three lines independently and needed no change; added `parsePinnedUnmanagedSkillCountsInBothBuckets` in HermesCuratorParserTests.swift to lock in the combination.
- [fact] `PROTECTED_BUILTIN_SKILLS` (tools/skill_usage.py) going empty is a genuine v0.21.0-only change (commit 0f3fcacd3f, present only at v2026.8.31, not at v2026.8.27) — `plan` graduated from a protected bundled skill to a first-class built-in command. Scarf's curator UI (CuratorView.swift, CuratorService.swift) never encoded a "protected builtin" concept in the first place (grepped for "protected"/"builtin" copy, badges, `is_protected_builtin`-equivalent logic — none found), so there was nothing to remove or gate for this item.
- [fact] `hermes-agent` becoming an essential skill (commit 3733e4aff5 "system prompt no longer references tools/skills the session can't use; hermes-agent skill is always kept") lands at v0.20.6 (present at v2026.8.27), not v0.21. `ESSENTIAL_SKILLS = frozenset({"hermes-agent"})` in `agent/skill_utils.py` is subtracted from every disabled-set read (`get_disabled_skill_names`, `skills_config.get_disabled_skills`) and write (`save_disabled_skills`). New `HermesCapabilities.hasEssentialHermesAgentSkill` (`isV0206OrLater`) is used to strip `"hermes-agent"` out of the disabled set `SkillsViewModel.load(essentialHermesAgentSkill:)` builds, so a stale/hand-edited config.yaml entry can't render the skill as OFF on a host that ignores it entirely.
- [fact] The v0.21.0 bundled-skills roster reorg (82→58 skills; `github/` merged into `software-development/github`; `mlops/` and `smart-home/` dropped; `web/` added — commit c49fa88b80, present only at v2026.8.31) has zero hardcoded references anywhere in the Scarf repo (`grep -rn "mlops\|smart-home\|github/github-pr-workflow"` across `scarf/` — no hits). `SkillsScanner`'s dynamic directory scan needed no change; confirmed rather than assumed.

## W6 — Session-preview parity, `_compressed_summary`, `gateway_heartbeats`, Bot Chat rename

- [fact] Hermes's session preview is NOT `substr(content,1,N)` of the first user row. It is two SQL halves in `hermes_state_common.py`: `_PREVIEW_ELIGIBLE_SQL` (:131) decides whether a row may BE the preview, `_PREVIEW_RAW_SELECT` (:145) decides what text to show, and `_shape_preview` (:166) trims + flattens CR/LF in Python. Ported to Swift as `SessionPreviewSQL` (ScarfCore/Services), used by all three Scarf preview call sites (`fetchSessionPreviews`, `dashboardSnapshot`, `sessionListSnapshot`).
- [fact] **Preview eligibility semantics** (the durable, non-obvious part): since v0.19, in-place compaction rewrites history so the earliest surviving `role='user'` row is frequently a *compaction carrier*, not a typed message. A row is INELIGIBLE when it is a pure carrier — content starts (after whitespace) with the long-form summary intro or `[CONTEXT SUMMARY]:`, or the same prefix appears immediately after `[END OF PRIOR CONTEXT — COMPACTION SUMMARY BELOW]`. A carrier stays ELIGIBLE only when authentic content survives: a standalone carrier that contains `--- END OF CONTEXT SUMMARY — …` with non-blank text after it (the "force-user" tail), or a merged carrier whose preserved prior half is non-blank. For those survivors the preview is the *authentic fragment* — the text after the end marker, or the prior half with its `[PRIOR CONTEXT — for reference only; not a new message]` header stripped.
- [gotcha] Hermes matches the WHOLE 204-character shared intro of `SUMMARY_PREFIX` (`agent/context_compressor.py` :231, split at `"Do NOT answer"`), not the bare `[CONTEXT COMPACTION — REFERENCE ONLY]` label, so an ordinary user message that merely opens with the bracketed label is not mistaken for a carrier. Current and historical long-form prefixes share that exact intro and diverge only after it. Character lengths verified against Python: intro 204, end marker 84, merged delimiter 49, prior-context header 55 — SQLite `SUBSTR`/`INSTR` on TEXT count characters, and Swift `String.count` agrees, so the em dashes need no byte correction. NB `HermesMessage.classifyCompactionSummary` deliberately keeps using the SHORT opener (different job: hydration-time bubble styling, where a false positive is cosmetic).
- [decision] `messages._compressed_summary` (v0.21, `hermes_state_common.py` :475) is DETECTED (`hasCompressedSummaryColumn` on both backends, following the `hasCompactedColumn` pattern) but deliberately unused by every Scarf query — pinned by a test. Rationale from Hermes's own reader usage: its sole consumer is `_rows_to_conversation` (`hermes_state.py` :12899/:12965) tagging rows when `include_summary_markers` is set; Hermes's own preview and listing SQL never consult it. Scarf already classifies carriers from content, which works on pre-v0.21 hosts where the column does not exist — consulting it would add a schema dependency without adding information.
- [decision] Scarf's preview subquery applies `(active = 1 OR compacted = 1)` (schema-gated, empty clause when the columns are absent) where Hermes applies NO active filter. Deliberate divergence: it drops a *rewound* first message (`active=0, compacted=0` — undone, no longer in the conversation) while keeping compaction-archived rows (`active=0, compacted=1`), which ARE the session's real first message soft-archived in place. Demanding plain `active = 1` would be wrong for exactly that reason.
- [gotcha] Eligibility must live INSIDE the `MIN(id)` aggregate, not as an outer filter — otherwise a session whose first row is a pure carrier loses its preview entirely instead of falling through to the next real turn.
- [decision] Not ported: Hermes's two skill-scaffold arms of `_PREVIEW_RAW_SELECT` (wider excerpt for `[IMPORTANT: The user has invoked the …]` rows, head+tail spliced around `SKILL_EXCERPT_JOINT`). They only pay off with `describe_skill_invocation`, which Scarf has no port of; a wider excerpt with nothing to interpret it is worse than today. Also not ported: `_PREVIEW_MAX_CHARS` (60) truncation with ellipsis — that is CLI column-width formatting, and Scarf's views truncate themselves.
- [fact] `gateway_heartbeats` (`hermes_state_common.py` :523-538, issue #94895) — per-backend liveness rows (`backend_id`, `pid`, `started_at`, `last_heartbeat`, `profile`, `host`) written by each `serve`/`tui_gateway` process; the startup orphan sweep consults it so an idle-but-alive backend sharing a state.db is not reaped, falling back to the old staleness predicate when no heartbeat row matches. Record-only this cycle: Scarf has no reader and no code was written for it.
- [fact] The "Bot Chat" rename refusal is a **DB-layer** guard, not CLI or ACP: `SessionDB._set_session_title` (`hermes_state.py` :10199-10215) raises a bare `ValueError` at the single write path every surface (CLI `sessions rename`, `/title`, gateway `session.title`, REST) funnels through. `hermes_cli/console_engine.py::_sessions_rename` (:1497) does not catch it, so Scarf sees a non-zero exit plus a raw traceback. `hidden` is the discriminator (`CANONICAL_BOT_CHAT_TITLE = "Bot Chat"`, :10066) — an ordinary VISIBLE session a user names "Bot Chat" renames freely, so Scarf cannot predict the refusal from the title and must react to the failure rather than pre-empt it in the UI. Handled by `SessionRenameFailure.message(for:)`, which also maps the uniqueness error (:10250) and otherwise falls back to the last non-empty output line.

- [fact] The Swift-generated `SessionPreviewSQL.eligiblePredicate()` was verified **byte-identical** to Hermes's own `_PREVIEW_ELIGIBLE_SQL` (3173 chars) by dumping both and diffing — a throwaway test wrote the Swift string, a one-liner `exec`'d `hermes_state_common` for the Python string. Worth re-running as the parity check next cycle; it catches literal/offset drift that behavioural tests can miss.
- [gotcha] This is the first Scarf SQL to embed multi-byte literals (four em dashes) and `X'0A'` blob literals. The remote backend ships SQL as text through a quoted heredoc into `sqlite3 -readonly -json`, and a mangled prefix fails SILENTLY (never matches) rather than erroring — so it is covered by an end-to-end test driving `RemoteSQLiteBackend` over `LocalTransport` against a real fixture DB, not a mock. `SQLValueInliner.inline` is quote-aware (a `?` inside a single-quoted literal is not treated as a bind placeholder, and `''` escapes are handled), so a future Hermes prefix containing a question mark would not misalign params.
- [gotcha] Old-schema previews are NOT byte-identical to pre-W6 Scarf, deliberately: `_shape_preview` parity trims and flattens CR/LF, so a multi-line first message now renders as one line. Carrier-stripping is content-based (not gated on any column) and is simply a no-op on pre-v0.19 content that has no carriers. The only schema-gated part is the `active`/`compacted` clause.
- [gotcha] Cost shape changed: the eligibility predicate (~6 `INSTR` + several `SUBSTR`/`LTRIM` per row) is now evaluated for every `role='user'` row inside the `MIN(id)` GROUP BY. The pre-W6 query already scanned all user rows, so it is added CPU per row rather than a new scan — but Hermes's own form is cheaper (a per-session correlated subquery with `ORDER BY … LIMIT 1` that short-circuits). Revisit if `mac.fetchSessionPreviews` ScarfMon timings regress on a large state.db.

- [gotcha] SQL prefix windows must be sized with `String.unicodeScalars.count`, NOT `String.count`. SQLite's `SUBSTR` on TEXT counts code points and Python's `len` does too, but Swift's `String.count` counts grapheme clusters — the three agree for today's literals (an em dash is one of each) but a future prefix carrying a flag, ZWJ emoji, or combining mark would make the Swift window shorter than the literal, and the equality could then never match. The failure mode is SILENT (carriers just stop being stripped), so `SessionPreviewSQL` counts scalars and a test pins all five lengths (204/18/84/49/55).
- [decision] Added a `INSTR(content, '[CONTEXT ') = 0 OR <eligible>` short-circuit in `firstEligibleUserRowSQL` — provably equivalent (every carrier shape must contain `[CONTEXT `, since both prefixes start with it and a merged carrier needs one after its delimiter). Composed AROUND `eligiblePredicate()` rather than folded into it, specifically so that expression stays byte-identical to Hermes's generated SQL and can keep being diffed. Measured on a 300k-message/102k-user-row fixture: old 0.067s, W6 without pre-filter 0.113s (1.68x), with it 0.103s (1.53x) — it recovers about a fifth of the added cost, not most of it. If `mac.fetchSessionPreviews` ever regresses for real, the fix is a different query SHAPE (per-session correlated subquery with `LIMIT 1`, as Hermes uses), not more predicate tuning.
- [fact] A session whose ONLY user rows are pure carriers now yields no previews-dictionary entry at all (rather than carrier boilerplate); callers fall back to title/session id via `previewFor`. Matches Hermes, and is the intended outcome, but it is the one user-visible shape change beyond cleaner text.


## W7 — Cron parity (jobs.json shapes, incidents, doctor, resume --run-now, bot-chat delivery)

- [gotcha] `hermes cron doctor` exits **1 when it finds issues** — that is the normal path, not a failure. Any Scarf caller must parse stdout regardless of exit code; gating the parse on `exitCode == 0` would silently show zero findings exactly when there are some. (`hermes_cli/cron.py::cron_doctor` returns 1 from the findings branch, 0 from the clean branch.)
- [gotcha] `supportsCronDeliver(_:)` had a real pre-existing hole: it version-gated only the `all` sentinel and returned `true` for everything else, so `--deliver bot-chat[:profile]` (v0.20.6+) forwarded to a pre-0.20.6 host would fail the WHOLE `cron create` at argparse. Fixed with an explicit `bot-chat` / `bot-chat:` prefix branch on `hasCronBotChatDelivery`. The two callers that matter are `FleetApplyPlan` (apply-cron) and `ProjectTemplateInstaller` — both copy a job definition to another host, which is the only way a value the local UI accepted reaches a host that can't parse it.
- [fact] `cron/jobs.py::load_jobs` (v0.20.6+) tolerates three on-disk shapes and auto-repairs two of them: canonical `{"jobs":[…]}`, an id-keyed map `{"jobs":{"<id>":{…}}}` (flattened with `{**v, "id": v.get("id") or k}` — inline id wins, map key adopted otherwise, non-dict values skipped with a warning), and a bare top-level array. `CronJobsFile.init(from:)` now reads all three. Scarf orders the flattened map by MAP KEY, not resolved id, so an unordered JSON object doesn't shuffle the board between reloads.
- [decision] The id-keyed-map fallback only engages when `jobs` really decodes as a `[String: JSONValue]`. A `jobs` ARRAY carrying one undecodable job rethrows the ARRAY error rather than the "not a dict" error — otherwise a corrupt-single-job store gets mis-diagnosed and the next reader hunts the wrong bug. Pinned by `arrayWithABadJobRethrowsTheArrayError`.
- [fact] `repeat` needed no decoder change — it is unmodeled and rides in `HermesCronJob.extra` as a `JSONValue`, so bare `"forever"`/`"once"`/int forms already decoded and round-trip **verbatim** (Scarf must not normalize on Hermes's behalf). The gap was READ-side: added `repeatSpec` + `normalizeRepeatValue`, a port of `cron/jobs.py::normalize_repeat_value` (forever/infinite/inf/none/"" → nil; once/one/1x → 1; numeric string or int → itself; `<= 0` → nil). Note Scarf folds unparseable input to nil where Hermes raises — a UI read path must not throw.
- [fact] `monitor_script` / `monitor_url` / `monitor_state` / `provider_snapshot` / `model_snapshot` survive decode→encode untouched via the existing generic `extra` passthrough — verified through `withEnabled(false)` (the pause/resume copy, historically where strips happened), including nested objects/arrays and explicit `null`s. No fix was needed; the test is the regression guard.
- [fact] Terminal-job activation is refused in TWO places, with different wording: `update_job` raises "Cannot activate terminal cron job '<name>' through update_job; use cron resume --run-now or --at" (cron/jobs.py:2593/2694) and `trigger_job` raises "Cannot run: job '<name>' is <state> (terminal)" (:2760). `resume_job` funnels through `update_job`, so plain Resume hits the first. `CronViewModel` pre-checks `job.isTerminal` on both Resume and Run Now, plus `friendlyCronFailure(_:)` as a post-hoc net for a job that turned terminal between load and click.
- [gotcha] A terminal job can still have `enabled == true`, so the detail pane offers "Pause" for it — and pausing a completed job ALSO trips the terminal guard (the merged record's state leaves `{completed, error}`). That is why the friendly-message translation exists on the generic `runAndReload` path and not only on the two pre-checked verbs.
- [gotcha] `CronView` reads capabilities from an async-probing store, so `onAppear` can run before the version answer lands. The gated probes (`loadIncidents`/`loadDoctor`) and `viewModel.supportsResumeRunNow` are re-run from `.onChange` on each capability — without that, a cold launch shows no incidents, no doctor findings, and the wrong terminal-refusal wording.
- [fact] `hermes cron runs` output format is UNCHANGED at v0.21.0 (same f-string in `cron_runs`), so `HermesCronRunsParser` needed no edit; `cronRunsFormatUnchangedAtV021` is the drift alarm. Neither `cron incidents` nor `cron doctor` has a `--json` flag, so both are text parsers. ANSI is stripped defensively even though `hermes_cli/colors.py::should_use_color` requires a tty (always false for Scarf's piped runs).
- [convention] Cron UI strings were plain Swift literals when W7 shipped (matching the then-precedent). SUPERSEDED 2026-09-01: the post-v2.24 backfill (bb9dc7c-era work, commit e8c58ae) converted Cron's view-layer literals into the catalog; remaining String-typed component params were the extraction leak fixed in the 2026-09-02 section-audit cycle.


## W8 — dotted-key escaping for interpolated config-key segments (t-01d5c11b)

Pre-existing bug: user text interpolated into a `hermes config` dotted key path (quick command names, credential-pool provider ids) could contain a literal `.`, which `hermes config set` (pre-v0.21) or even v0.21's `_split_key_path` (unescaped) treats as a nesting separator — corrupting `config.yaml` (e.g. a quick command named "v1.2 deploy" wrote `quick_commands.v1.2_deploy.type` as 3 levels of nesting instead of one key with a dot in it).

- Hermes v0.21 semantics (`hermes_cli/config.py`, verified in the v0.21.0 audit checkout): `_split_key_path` treats a backslash before a dot (`\.`) as a literal dot within the current segment; unescaped dots still split. `_greedy_literal_match` additionally prefers an existing longest literal dotted key when *reading/navigating* an existing structure (so `providers.qwen3.5-397b.api_key` finds the real `qwen3.5-397b` entry without any escaping, as long as that key already exists) — but a *new* write with an unescaped dot still creates nested maps. `_phantom_sibling` makes `_set_nested` raise `ValueError` instead of silently shadowing an existing dotted-literal key when about to create a colliding intermediate mapping.
- New shared helper: `ConfigDottedKeySegment.escaped(_:capabilities:)` in `Packages/ScarfCore/Sources/ScarfCore/Services/ConfigDottedKeySegment.swift`. On `capabilities.hasConfigDottedKeyEscape == true` (v0.21+) it backslash-escapes `.` → `\.` in the segment; on older/undetected (`.empty`) capabilities it strips dots out entirely (no escape syntax exists pre-v0.21, so stripping is the only corruption-safe option). Folds in the pre-existing space→underscore sanitization so callers don't duplicate it. Dot-free input is untouched on every host generation (verified byte-identical).
- Argv verification: Scarf never shells out through a string — `LocalTransport.runProcess` execs `Process` with an args ARRAY (no shell), so a `\.` in one argv element survives verbatim. The SSH remote path (`SSHTransport.composedRemoteCommand` → `remotePathArg`) DOES round-trip through `sh -c`, but `remotePathArg` doubles every backslash (`\`→`\\`) before double-quoting specifically so escaped bytes survive shell parsing intact — so the same escaped-segment string is safe to pass to `runHermes` unconditionally regardless of local vs. remote transport; callers don't need transport-specific handling.
- Applied at the two interpolated-segment writers found by repo-wide grep for `"config", "set"` with `\(`-interpolated dotted keys: `QuickCommandsViewModel.addOrUpdate` (`quick_commands.<name>.type/.command`) and `CredentialPoolsViewModel.setStrategy` (`credential_pool_strategies.<provider>`, applied defensively — provider is normally a fixed id today). No other interpolated dotted-key writers exist (`SettingsViewModel`, `LocalModelConfigPlan`, `PlatformSetupHelpers` all use static/fixed keys, not user text).
- Read-side bug that must be fixed together with the write-side escape: `QuickCommandsViewModel.loadQuickCommands` used to `key.split(separator: ".", maxSplits: 2)` on the flattened `quick_commands.<name>.<field>` path — this breaks for any name containing a literal dot (the on-disk YAML key created by an ESCAPED write, e.g. `v1.2_deploy:`, is a real dotted string; `HermesYAML.parseNestedYAML`'s flattening just joins segments with `.`, so it's indistinguishable by dot-count from 3-levels-deep nesting). Fixed by peeling the known `.type`/`.command` suffix off the remainder instead of positional splitting, so everything in between (dots included) is the name. This also happens to recover names from PRE-v0.21 already-corrupted (nested) nested entries as a best-effort merge rather than dropping them.
- Quick commands have no CLI-based delete path today (`openConfigForRemoval` just opens config.yaml in the editor) — so there is no delete-side interpolation to fix; only write + read.
- Capability lookup for both call sites: `HermesVersionCache.shared.cached(for: context) ?? .empty` — synchronous, no subprocess; `.empty` capabilities correctly resolve `hasConfigDottedKeyEscape == false`, so an as-yet-unprobed host safely falls back to the strip-dots (old-host) behavior rather than assuming v0.21 semantics.

Source paths: `scarf/Features/QuickCommands/ViewModels/QuickCommandsViewModel.swift`, `scarf/Features/CredentialPools/ViewModels/CredentialPoolsViewModel.swift`, `Packages/ScarfCore/Sources/ScarfCore/Services/ConfigDottedKeySegment.swift`, `Packages/ScarfCore/Sources/ScarfCore/Services/HermesCapabilities.swift`, `Packages/ScarfCore/Sources/ScarfCore/Transport/SSHTransport.swift`, `Packages/ScarfCore/Sources/ScarfCore/Transport/LocalTransport.swift`.


## W9 — Peers surface (`hermes peer`, gated `hasPeerRunCommands`)

- [decision] The Peers surface is a **sidebar section in Manage, inserted between Gateway and Cron**, gated on `hasPeerRunCommands` (v0.21 floor) in `SidebarView.sections`. Rationale: Gateway is this machine's *inbound* messaging surface, Peers is its *outbound, machine-to-machine* counterpart, so they read as a pair. `SidebarView` is the ONLY construction site for sections (`grep SidebarSection.allCases` / `SidebarSection(rawValue:)` across `scarf/scarf` → zero hits), so gating there is complete — there is no command palette or settings enumeration to gate separately.
- [decision] The peer registry is read from `config.yaml` `bot_peers:` via `HermesConfigReader.readRawConfig` + a new `HermesBotPeersYAML.parse(yaml:)`, **not** from `hermes peer list`. `peer list` has no `--json` mode and, worse, annotates every row with "key set"/"NO KEY", which requires resolving the credential (`_peer_secret` → profile secret store or env). Reading the file keeps Scarf structurally incapable of touching a peer key. `HermesBotPeer` models only `name`/`url`/`note`; it exposes `keyEnvName` (a pure port of `_peer_key_env`: uppercase, `-`→`_`) as the safe, actionable half of "is the key configured?" — the *name* to set in `~/.hermes/.env`, never a value or a presence probe. A key hand-pasted into config.yaml has nowhere to land in the model (pinned by a test).
- [gotcha] **`hermes peer run` writes to stderr on the happy path.** `_peer_run_durability` calls the peer's `/v1/capabilities`; when `features.runs_idempotency.durable` isn't advertised — which includes every peer too old to expose the endpoint at all, i.e. most of them — `cmd_peer` prints "Warning: this peer does not advertise restart-durable run replay…" to stderr and then proceeds normally. Any caller that treats non-empty stderr as failure breaks `run` against real peers. `HermesPeerCLI` judges success by **exit code only** and hands the warning back separately via `durabilityWarning(inStderr:)`; on a genuine failure that line is stripped out of the error message as noise.
- [gotcha] An HTTP 400 out of `_ensure_bot_chat` becomes a `RuntimeError` whose sentence is the actual remedy ("Peer already has a 'Bot Chat' session but it is hidden and the peer's gateway is too old to expose hidden sessions to this lookup … Update the peer's hermes-agent, or unhide the session there: PATCH /api/sessions/<id> {\"hidden\": false}"). It reaches Scarf only as stderr text, differently framed per verb (`dm` catches RuntimeError → "Peer 'x': …"; `run` folds it into the `URLError/OSError/RuntimeError` arm → "Could not reach peer 'x': …"). So `HermesPeerCLI.Failure.message` is the CLI's **stderr verbatim** (stdout fallback), never a paraphrase — the same rule saves the missing-key error, which names the exact `HERMES_PEER_<NAME>_KEY` variable to set.
- [fact] Exit-code contract (from the subcommand's own epilog, and matched by every branch of `cmd_peer`): 0 ok, 1 delivery/peer error, 2 usage. Mapped to `Failure.Kind.delivery`/`.usage`, with everything else (including `runHermesCLISplit`'s -1 transport sentinel) as `.local`. A **failed run is exit 0**: `peer status` returning `{"status":"failed","error":…}` is a successful CLI invocation carrying a remote failure, and must not be conflated with the CLI failing to reach the peer.
- [decision] Peer **add/remove was skipped** (it was optional this cycle). `hermes peer add` takes `--key` and is the natural place a user expects to enter one; an add flow that omits the key produces a registered peer that every verb then refuses with "No API key for peer 'x'". Rather than build a half-flow Scarf can't complete, the empty state prints the exact `hermes peer add … --key <API_SERVER_KEY>` line and the rows name their `.env` variable. Registration stays a CLI act, consistent with the rule that Scarf never handles credentials.
- [fact] Peer run handles are **memory-only, per view model**: `hermes peer` has no "list runs" verb, so the `run_id` returned by `peer run` is the sole handle. `PeersViewModel` is therefore coordinator-cached (like Cron) so the rows survive section switches, and the UI says so. A replayed run (same idempotency key) replaces the existing row rather than duplicating the handle.
- [convention] Peers UI strings are plain Swift literals, matching the Webhooks/Credential Pools/Cron precedent. `SidebarSection.peers.displayName` ("Peers") is a new `LocalizedStringResource` with no `Localizable.xcstrings` entry yet — left for the periodic l10n backlog pass (the catalog is extraction-driven; an untranslated key falls back to base).


## Fixups (fresh-eyes audit)

Durable gotchas found auditing the v0.21 parity branch. Each is a property
of Hermes's own output/CLI contract, so they outlive the branch.

**`cron doctor` output is not line-oriented.** `_cron_doctor_issues_for_job`
emits `f"last run failed: {last_error}"`, and for a script job the scheduler
stored `last_error` as `"stderr:\n" + stderr` (`cron/scheduler.py:4457-4458`)
— a whole Python traceback. `hermes_cli/cron.py:674` interpolates that into
`f"    - {issue}"`, so **only the first physical line of an issue carries the
bullet**; the rest land at the traceback's own indentation (often 0 or 2).
Any parser must be indent-based — job header at indent 2, bullet at indent 4,
everything else a continuation of the issue in progress. A traceback line can
sit at indent 2 (`  File "…"`), so telling a header from a continuation needs
a job-id shape check (`uuid4().hex[:12]`, or a slug with a digit); `File`,
`Traceback`, `raise`, `KeyError:` all fail it.

**`cron doctor` exit code is not a success signal.** It exits **1 on the
normal "found issues" path**. Judge a run by its sentinels (`Cron doctor
found …` / `✓ Cron doctor found no issues`), never by the exit code — and
only memoize a run that produced one, or a transient failure gets cached
forever as "no findings".

**`cron incidents ack` exits 0 on the miss path.** When `ack_incident`
returns falsy the CLI prints `Incident <id> not found or already closed.` in
yellow and still `return 0` (`hermes_cli/cron.py:322-335`). The output text is
the only discriminator; exit code alone reports a no-op as a success.

**argparse positionals need `--`.** `peer dm` / `peer run` take `message` as
a positional (`nargs="?"`), so a message beginning with a dash binds to a
flag. Insert argparse's standard `--` end-of-options marker before the
positionals — no Hermes-side change needed. It must come **last**: argparse
treats every token after the first `--` as positional, so any flag
(`--json`, `--idempotency-key`) has to sit in front of it.

**`gateway_state.json`'s pid is not proof of life.** Nothing rewrites it on
an unclean exit, so a crash or `kill -9` leaves a stale pid behind.
`hermes gateway status` is the live probe (`get_gateway_runtime_snapshot()`);
its `✗ Gateway is not running` (`hermes_cli/gateway.py:8958`) must beat the
pid. Service-managed branches print neither marker, so the pid stays the
liveness signal only there.

**The cron terminal-job guards are v0.20.6, not older.** Verified absent at
tag `v2026.8.19`, present at `v2026.8.27`. A client-side "can't resume a
completed job" pre-check must therefore be gated on `isV0206OrLater` — on an
older host that operation actually succeeds, and refusing it locally denies
something the host would have accepted.

**PyYAML line-folds long scalars.** A long `--note` round-trips through
`_save_peers` as a folded scalar whose continuation lines sit *deeper* than
their key — and PyYAML dumps keys sorted, so `note` precedes `url`. A note
containing `url: http://decoy` therefore parsed as a sibling key and
overwrote the peer's real URL. In valid YAML a key can never be indented
deeper than the sibling scalar before it (that requires a parent with an
empty value, i.e. a section header), so "deeper than the last scalar at this
level" is an unambiguous continuation marker — that's the rule `HermesYAML`
now uses.

**`normalize_repeat_value` is v0.21.0, not v0.20.6** (an earlier comment said
otherwise). It doesn't matter for gating: Scarf's `repeatSpec` is a read-side
interpreter of what's already on disk, and a pre-0.21 store can hold the same
bare values, so the reader is version-independent by design.

**Deliberate non-changes.** `ConfigDottedKeySegment` strips dots when the
capability probe hasn't landed yet (an unprobed v0.21 host). That is the
correct failure direction and must not be "fixed": stripping is lossy but
never corrupting, while guessing "escape" on a pre-0.21 host reproduces
hermes-agent #84064. Also left alone: the session-preview active/compacted
filter divergence, peer names containing dots, and the
`runtime_metadata_footer` removal.
