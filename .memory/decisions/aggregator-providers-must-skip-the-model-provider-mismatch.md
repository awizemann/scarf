## Observations
- [bug] GH issue #121: Scarf 2.15.0 showed a false "Model/provider mismatch in config.yaml" banner for a valid OpenRouter config (`model.provider: openrouter`, `model.default: xiaomi/mimo-v2.5`). Both one-click fix buttons would have corrupted the working config. #chat #preflight
- [root-cause] `ModelPreflight.detectMismatch` (ScarfCore/Services/ModelPreflight.swift) treated ANY slash in `model.default` as a stale provider prefix. Aggregator providers namespace model IDs as `org/model` natively — the slash is part of the model ID, not a provider prefix. #root-cause
- [decision] Skip the mismatch check entirely when `model.provider` canonicalizes to a Hermes aggregator. Set mirrors `is_aggregator = True` in hermes_cli/providers.py: openrouter, opencode, opencode-go, kilo, huggingface, novita, vercel; plus the bare `openai` → `openrouter` alias from Hermes ALIASES. Held in `ModelPreflight.aggregatorProviders` (static let) and `ModelCatalogService.providerAliases`. #decision
- [kept] The original stale-prefix detection for DIRECT providers (e.g. `anthropic/claude…` under `gemini` → -32603 at first prompt) still fires — pinned by `detectMismatchStillFiresForNonAggregatorProviders`. #regression-guard
- [correction] (S06-F1, R03, 2026-09-26) This bullet used to cite `anthropic/…` under **`nous`** as the direct-provider case — that premise was WRONG. `nous` is in `hermes_cli/model_normalize.py:30-32` `_AGGREGATOR_PROVIDERS` ("Providers whose APIs consume vendor/model slugs": openrouter, nous, ai-gateway, kilocode) at every tag since the file appeared (≤ v2026.4.8), and Nous's own catalog ids are vendor-prefixed (`website/static/api/model-catalog.json` providers.nous). `providers.py` gives nous an overlay WITHOUT `is_aggregator`, so mirroring `is_aggregator` alone missed it and every Nous user got a false banner whose "Use anthropic" moved them off Nous. `nous` is now in `ModelPreflight.aggregatorProviders` (ai-gateway/kilocode were already covered canonically as vercel/kilo). The source of truth is the UNION of `is_aggregator` overlays and `model_normalize._AGGREGATOR_PROVIDERS` canonicalised through ALIASES; `check-hermes-tables.py` lane 2 diffs against both and fails closed on a reshaped set. #correction #nous
- [decision] (R03) Vendor-STRIPPING providers are a second skip class, separate from aggregators: Hermes normalises every non-aggregator model before sending (`agent/agent_init.py:460-462` @ v2026.9.24), and for `copilot`/`copilot-acp` `normalize_copilot_model_id` drops ANY vendor prefix (verified: `anthropic/claude-sonnet-4.6` → `claude-sonnet-4.6`), while `openai-codex` drops only `openai/`. `ModelPreflight.vendorStrippingProviders` = canonical `github-copilot`, `copilot-acp`, plus the codex+`openai` case, gated on `hasVendorPrefixStrippingForCopilot` (v0.12.0 — `normalize_copilot_model_id` first called from model_normalize at v2026.4.30). Not in lane 2 (flat namespace, not an aggregator). `nvidia` (catalogue prefix repair, natively namespaced NIM ids) is a candidate for the same treatment — not changed. #decision #copilot
- [fact] (R03) Existing `provider: llamacpp` + a base_url other than 127.0.0.1/localhost:8080 on v0.21.1+ raises a separate chat banner (`ModelPreflight.llamaCppBaseURLIgnored`) with a one-click plan-routed switch to `custom`; never migrated silently. #llamacpp
- [sync] On every Hermes bump, reconcile `ModelPreflight.aggregatorProviders` + `ModelCatalogService.providerAliases` against hermes_cli/providers.py `is_aggregator` flags AND `hermes_cli/model_normalize.py` `_AGGREGATOR_PROVIDERS`, plus ALIASES — same cadence as the ModelCatalogService tables (`scripts/check-hermes-tables.py` lane 2 does both). #maintenance
- [fix] Landed on main as d1285b0 (2026-07-03) with tests in ModelPreflightTests. #fixed

## Follow-up hardening (6a12139, 2026-07-03)
- [decision] The banner's "Use <prefix>" one-click fix is now validated: `detectMismatch(_:knownProviders:)` takes the canonical provider roster (models.dev catalog + overlays via `ModelCatalogService.loadProviders()`) — **correction (S06-F1, B02, 2026-09-27): "in the models.dev catalog" never meant "a provider Hermes has".** Of 223 cached models.dev keys only 38 route at v2026.9.24 (`auth.resolve_provider` raises "Unknown provider" for `mistral`, `groq`, `cerebras`, … — `hermes_cli/auth.py:1500-1509`), so before B02 the "Use <prefix>" button could write an unroutable provider. On hosts with `hasRoutableProviderTable` (v0.6.0+ since B02b, per-version bands) `loadProviders()` now drops unroutable ids (`HermesRoutableProviders`), which makes this roster Hermes-accurate there; only undetected hosts keep the full catalog; an unrecognized prefix still fires the banner but sets `prefixIsKnownProvider = false`, and ChatView hides the "Use <prefix>" button (which would have written a nonexistent provider) leaving only the strip fix + an aggregator hint. #decision
- [decision] `ModelCatalogService.providerAliases` + `canonicalProviderID(_:)` are a verbatim mirror of hermes_cli/providers.py ALIASES / normalize_provider. detectMismatch canonicalizes BOTH prefix and provider before comparing, so alias pairs (`claude/…` vs `anthropic`, `x-ai/…` vs `xai`, provider `zhipu` vs `zai/…` prefix) no longer false-positive. Reconcile this table on every Hermes bump. #maintenance
- [gotcha] The roster must be ignored when only overlay providers loaded (fresh install, `models_dev_cache.json` not yet written by Hermes) — otherwise real providers like `anthropic` read as unknown and the primary fix button disappears. ChatViewModel checks `contains(where: { !$0.isOverlay })` and caches the result per VM because the catalog read can be a multi-megabyte SSH pull; roster load is deferred to the rare mismatch-detected path. #gotcha


## Verification + mechanical gate (2026-07-04)
- [fact] (2026-07, historical — that checkout path is RETIRED; tag walks now use `~/.hermes/hermes-agent`) The then-vendored Hermes checkout at ~/Developer/ScarfBox/Vendor/hermes-agent sat exactly on the `v2026.6.5` tag (commit 3c231eb39, "chore: release v0.16.0"), clean tree — the mirrored tables match Scarf's v0.16.0 target precisely, not a newer working copy. #verified
- [decision] `scripts/check-hermes-tables.py` now mechanically diffs the hand-mirrored tables against hermes_cli source: providerAliases ↔ ALIASES incl. changed mappings, aggregatorProviders ↔ is_aggregator overlays, overlayOnlyProviders ↔ overlays absent from models.dev. Missing entries FAIL (exit 1); Scarf overlays that models.dev has since absorbed only WARN (dormant fallback — loadProviders() lets the catalog entry win). **The script is currently 8 lanes** (was 6 post-R08), reads Hermes at a TAG via `git show` by default (`--tag`, defaulting to `HERMES_TARGET_TAG`; `--worktree` opts into the working tree), and a SKIPPED lane is no longer a pass — it prints `SKIPPED lane N: <reason>` and exits **2**, with `lanes=N/8` on the verdict line. Lanes 7–8 (MCP catalog and routable providers) were added after R08. `lanes=8/8` + exit 0 is the only result that clears the gate; `--allow-skip` is an escape hatch for a deliberately-partial host, never for the gate. An absent `agent/models_dev.py` SKIPs; a present-but-unparseable one `sys.exit`s. Script tests: `python3 -m unittest discover -s scripts/tests -t .`. #decision
- [decision] Dormant overlays are KEPT deliberately (d04d5bf): `lmstudio` and `tencent-tokenhub` are now in models.dev so their overlayOnlyProviders entries only merge on stale-cache hosts — but Scarf supports Hermes back to v0.6, Hermes v0.16 still ships both in HERMES_OVERLAYS, and the model-ID validator's overlay fall-through (ModelCatalogService.swift ~L385) was designed for exactly this catalog evolution. Entries are annotated in-source; check-hermes-tables.py WARNs on them by design — a WARN there is policy, not drift. #decision

## Capability-gated removed-provider fallback (2026-09-26)
- [decision] Hermes removed `opencode-free` aggregator (and OpenAI-Codex aliases) at v0.21.4. Scarf's check-hermes-tables.py enforces literal sync against the current target tag (v2026.9.24), so these entries were deleted from `aggregatorProviders` / `providerAliases` / overlayOnlyProviders — but older connected hosts still running removed providers need them. Solution: capability-gated legacy tables. `legacyAggregatorProviders` and `legacyProviderAliases` hold removed entries, consulted only when `HermesCapabilities.hasOpenCodeFreeProvider` (undetected hosts + pre-floor versions) is true. The same pattern gates removal across: `aggregatorProviders(capabilities:)` function replaces the static let, `ModelCatalogService.legacyProviderAliases` consulted before `providerAliases` in `canonicalProviderID(_:capabilities:)`, and legacy-only overlays in `legacyOverlayOnlyProviders`. Every existing unconditional caller uses `.empty` capabilities default, resolving exactly as before — byte-identical for undetected hosts. Landed via commit 734381b1 (2026-09-26). #decision
- [verified] scripts/check-hermes-tables.py --tag v2026.9.24 reports "OK aliases=87 aggregators=8 overlays=25 env-vars=54 mcp-catalog=65 routable=194 lanes=8/8" (8 lanes added post-R08, including lane 7: MCP catalog sync, lane 8: routable providers). All legacy tables check. #verified


- [decision] (R16c, 2026-09-27) Direct providers whose own API serves `vendor/model` ids skip the mismatch too, via a SEPARATE `ModelPreflight.vendorNamespacedProviders` set (not `aggregatorProviders`, which check-hermes-tables lane 2 diffs). Today only `nvidia` (NIM serves `nvidia/…`, `meta/…`, `z-ai/…`): nvidia is in no prefix-stripping set at any tag and `_repair_prefix_from_catalogue` only touches bare ids (`hermes_cli/model_normalize.py:72-82,171-175,257-258` @ v2026.9.24; file first appears v2026.4.8, ids went out as typed before), so the skip is unfloored. #nvidia
