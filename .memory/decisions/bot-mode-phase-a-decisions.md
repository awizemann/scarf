B4 filled BotDetailView's `automation` slot (commit 5c26a90): per-bot Routines + a Remote peer roster group.

## Observations
- [fact] Verified routine prefix format: Hermes Desktop scopes a cron job to a bot by NAME, matched with BOT_TAG_RE = /^\[bot:([a-z0-9][a-z0-9_-]*)\]\s*/i (hermes-bots/cron.tsx:73; compose side at cron.tsx:970 uses `[bot:${profile}] ${title}`). BotRoutinePrefix (ScarfCore) mirrors this exactly via NSRegularExpression with caseInsensitive — tag must be at the START, slug is [a-z0-9][a-z0-9_-]* only (brackets/unicode/leading dash-or-underscore never match) #b4 #verified
- [decision] BotRoutinesViewModel wraps a CronViewModel instance per bot (memoized in BotsViewModel.routinesCache[profileName]) and only FILTERS cron.jobs by BotRoutinePrefix.matches — pause/resume/run-now/create all delegate straight to CronViewModel's own W7 methods (terminal-state pre-check, isV0206OrLater gate) rather than reforking any cron argv or gating logic #b4
- [decision] Create-routine sheet composes --name "[bot:<name>] <title>" and gates --deliver bot-chat:<profile> on hasCronBotChatDelivery (isV0206OrLater) — omits --deliver entirely below that floor rather than emitting a flag the host can't parse, with a caption noting output isn't auto-routed. Kept deliberately minimal (title/schedule/prompt only); power users use the full Cron section #b4
- [decision] Remote roster group reuses W9's HermesBotPeersYAML/HermesPeerCLI/PeersViewModel UNMODIFIED via BotsViewModel.peers (hand-rolled lazy var, since @Observable can't synthesize `lazy var`). Gated on hasPeerRunCommands (isV021OrLater). Selection state is a SEPARATE var (peers.selectedPeerName) from the local roster's selectedProfileName, with each row's tap handler clearing the other — so a peer named the same as a local bot can never route into local-profile code paths (BotsService, ACP pinning, avatar I/O); opening a peer shows a DM/async-run pane, never the ACP conversation #b4 #wrong-profile
- [decision] Both W7 (CronViewModel) and W9 (PeersViewModel) were reused wholesale rather than reforked for B4 — the app-target BotsViewModel/BotRoutinesViewModel own only the bot-scoping filter and the memoization/selection-separation wiring around them #b4

## Fixups (fresh-eyes audit)

- [fact] **The YAML newline trap.** `HermesBotProfileYAML.quoted` emitted single-quoted scalars, which have NO escape for a line break — so any multi-line value (the editor's "Role" `TextEditor`) wrote a real newline inside `'…'`. Verified against PyYAML 6.0.3, that fails two ways: (1) common case — YAML line folding silently rewrites interior newlines to spaces and blank lines to one newline, and since Scarf re-reads before the next save the mangled form is what persists (cumulative, invisible); (2) sharp case — a line that is exactly `---` or `...` (routine in pasted markdown) terminates the document mid-scalar, PyYAML raises on the WHOLE file, and Hermes' `read_profile_meta` swallows the exception into empty defaults, so `display_name`/`description`/the entire `hermes-bots` block vanish and the profile drops out of the bot roster. Fix: any value carrying a C0 control, DEL, NEL, LS or PS is emitted as a **double-quoted** scalar with `\n`/`\t`/`\xNN`/`\uNNNN` escapes, with a local `unquote` (NOT the shared `HermesYAML.stripYAMLQuotes`) as its exact inverse. Do NOT "fix" this by flattening the description instead: Hermes writes `ui_meta` through `atomic_yaml_write` → `yaml.safe_dump`, which round-trips real newlines fine, so flattening would destroy user content to work around a writer bug. Only genuinely single-line fields (title/color/shape) are collapsed, in `BotDraft.singleLine`. Regression-tested by shelling out to real PyYAML, not by Scarf's own parser #fixup #verified #yaml
- [decision] **`ServerContext.pinnedToProfile` semantics: nil/""/"default"/invalid means the ROOT home, not "unchanged".** It previously returned `self`, which is only correct when `self` is already a root home. From a profile-scoped base — an SSH window scoped to `work` (#126), or a local host whose `active_profile` is `work` (`HermesPathSet.defaultLocalHome` resolves it) — returning `self` handed the **default bot** `work`'s `state.db` and spawned its ACP inside `work`'s home: the wrong-profile bleed the method exists to prevent, reached through the one input everyone assumes is inert. Every branch now root-normalizes first and returns that copy. The old guarding test could never have caught it because it started from a root base, where both answers coincide — a scoped-base test is the only one that bites #fixup #wrong-profile
- [fact] **Routine delegation wrapper (byte-pinned to Hermes Desktop).** `hermes cron` has ONE store per profile and runs every job AS that profile, so `[bot:x] <title>` name-scoping (`BotRoutinePrefix`) is presentation only — a routine created in the window profile's store with the raw instruction executes with the WRONG profile's memory/skills/credentials under the bot's name. Hermes Desktop solves this in `apps/desktop/src/plugins/hermes-bots/cron.tsx`: `SAFE_ROUTINE_MARKER = '[bot-mode:routine:v2] '` (:74) and `routinePrompt` (:270-286) wrap the instruction in `hermes -p <bot> chat -c 'Routine: <title>' -q '[Scheduled routine] <instruction>'` — but ONLY when `normalizedProfileName(bot) !== normalizedProfileName(activeProfile)` (trim + lowercase, :250-252), with POSIX `shellQuote` using the `'"'"'` escape (:254-256). `BotRoutineDelegation` (ScarfCore) mirrors all of it byte for byte so Scarf-created and desktop-created routines are interchangeable; the store profile is derived from the context home via `HermesProfileScope.profileName(forHome:)`. Change nothing in that string without re-reading the TS #fixup #verified #wrong-profile
- [fact] Two smaller traps worth remembering: ICU's `$` matches BEFORE a trailing line terminator, so `HermesProfileScope.isValidName("work\n")` validated and then normalized to `work` — validate-one-string/use-another. Fixed with a full-range match plus "a valid name equals its own normalization". And `locateBotBlock` takes the FIRST `hermes-bots` while PyYAML takes the LAST, so duplicates (and tab-indented `ui_meta` bodies, which this space-counting writer reads as an empty block and then appends a second block beside) are now refusals, matching the existing top-level duplicate-key guard #fixup


## Pre-release go/no-go fixups (commit be4f27d)

- [decision] **Routine outcome is typed, not sniffed.** `CronViewModel.message` is ONE string channel carrying both "Resumed" and "Failed: …"/`friendlyCronFailure`, and `BotRoutinesView` painted all of it `ScarfColor.success` with a 3s auto-clear — so a routine that failed announced itself in green and then vanished. Added `CronViewModel.MessageOutcome` + a single `post(_:outcome:autoClearAfter:)` write point (`message` is now `private(set)`, `dismissMessage()` is the explicit clear). Successes keep the 3s auto-clear; **failures never auto-clear** and get danger colour + a dismiss button in both `BotRoutinesView` and `CronView`. The auto-clear also re-checks that it still owns the channel, so a stale timer can't wipe a newer message #fixup #go-no-go
- [decision] **`demote` clears the `hermes-bots` block; `toggleHidden` is the separate verb.** demote used to route through `BotDraft.apply`, which stamps `isBotManaged = true` — making "Remove from Bots" byte-identical to Hide while the label promised removal. It now re-reads the identity and writes `isBotManaged = false` (plus `pinned`/`hidden` = nil, both of which live inside the block), which `HermesBotProfileYAML.write` already implements as "render an empty block → splice it out", including dropping an emptied `ui_meta:` header. Sibling namespaces and unknown keys survive; the profile returns to "Other profiles". Pinned by a real-PyYAML round-trip in `PreReleaseFixupTests` #fixup #go-no-go
- [fact] **Scarf must warn on a "Bot Chat" rename because Hermes won't.** `SessionDB._set_session_title` (:10210) refuses the rename only for a session that is titled "Bot Chat" **AND hidden**. Hermes Desktop mints its canonical chats hidden (gateway `session.create`, `hidden: true`); Scarf can only create one through the CLI, which never sets `hidden` — so for a Scarf-created Bot Chat the server-side guard never fires and the rename SUCCEEDS, orphaning the whole transcript (every surface re-resolves by exact title). `BotChatSession.renameNeedsConfirmation(currentTitle:newTitle:)` + `renameWarning` gate both rename paths (`SessionsViewModel.confirmRename`, `ChatSessionListPane.commitRename`). Plain exact-title check, deliberately NOT scoped to bot-managed profiles — the Sessions list has no profile context. Related copy fix: the chat appears in Sessions only while the window is scoped to THAT bot's profile (its `state.db`), not the current profile's list #fixup #go-no-go #verified
- [fact] **Bot Chat CREATION is floored at v0.21, above the `hasBotMode` v0.20.3 floor.** Per-flag verification of `hermes -p <bot> chat --in ~ -c "Bot Chat" --create-if-missing -Q --query-file <path>` at tag v2026.8.16.2 (0.20.3): `-c/--continue` (`_parser.py:401`), `--create-if-missing` (:410), `-Q/--quiet` (:368) and `--in` (:390) all PRESENT — but **`--query-file` is ABSENT** (`git grep query-file v2026.8.16.2` returns nothing; the chat parser there has only `-q/--query` at :304). It first appears at v0.21 (`_parser.py:362`). argparse rejects the whole invocation on an unknown flag, so the creation path is gated on the new `HermesCapabilities.hasBotChatCreationCLI` (`isV021OrLater`) with an explicit unsupported note; `-q <text>` is NOT a substitute because the body is arbitrary user text riding a remote `bash -lc`. Reading/messaging an EXISTING Bot Chat goes over ACP and stays on the `hasBotMode` floor #fixup #go-no-go #verified
- [gotcha] **A composed chat VM needs its capabilities store attached explicitly.** `BotConversationViewModel` reuses `ChatViewModel` wholesale, but the `attachCapabilitiesStore` call lives in `ChatView`'s `.task(id: capabilitiesStore?.capabilities.versionLine ?? "")` — not in the VM — so every bot conversation ran with `.empty` capabilities and a permanently degraded slash menu. `BotConversationView` now makes the identical call. Rule: when composing main-Chat's VM into a new surface, audit `ChatView`'s `.task`/`.onAppear` wiring, not just the VM's initializer #fixup #go-no-go
