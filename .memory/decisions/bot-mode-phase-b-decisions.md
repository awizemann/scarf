Shared log for the Bot Mode Phase B cycle (per-bot AGENT configuration: model pin, skills/toolsets/MCP enablement, SOUL.md). P0 = the ScarfCore foundation, `BotAgentConfigService` + `BotAgentConfig`. All findings source-verified at Hermes tag v2026.8.31 (0.21.0).

**The layering verdict (P0's headline, decides the whole UI story).** A Hermes profile does NOT inherit the root profile's `config.yaml` at runtime. `_load_config_impl` (`hermes_cli/config.py:3936-4080`) merges exactly three layers: `DEFAULT_CONFIG` → `<HERMES_HOME>/config.yaml` → the managed scope (`/etc/hermes`). Under `hermes -p <bot>`, `HERMES_HOME` IS `<root>/profiles/<bot>`, so layer 2 is the bot's own file and the root's is never opened. The only relationship is a one-time COPY at creation (`create_profile` with `--clone`, or `_seed_model_config`, `profiles.py:773-805`, copying the active profile's `model:` block into a clone-less new profile). So a "pin" is an override over **Hermes' built-in defaults**, never over root-profile values, and a UI that renders the root's model as the bot's inherited default is lying. Scarf therefore never reads the root's config on a bot path.

## Observations

- [fact] `hermes -p <bot> config get` prints the EFFECTIVE value (`get_config_value` → `load_config()`, config.py:6000-6012) with no way to tell a user pin from a DEFAULT_CONFIG fallback — so per-bot READS go direct to `<profile_dir>/config.yaml` via the transport (matching how the root path already reads: SkillsViewModel.readDisabledSkillNames, ToolsViewModel.loadPlatforms, HermesConfigReader) and per-bot WRITES go to the CLI (matching HermesFileService.saveModelConfig / SettingsViewModel). The raw file is the only honest source for pinned-vs-default #p0 #verified
- [gotcha] `-p` is passed on EVERY invocation including `default`. SSHTransport emits `HERMES_HOME=` only for a profile-shaped remoteHome (nothing for the root), and LocalTransport emits none at all — so without the flag, step 2 of `_apply_profile_override` follows the host's sticky `~/.hermes/active_profile` and the DEFAULT bot's `config set` lands in whatever profile happens to be active. `resolve_profile_env("default")` returns the root exactly (profiles.py:2513-2514), so the flag is precise, not just defensive #p0 #wrong-profile
- [fact] `-p` composes with every verb used: `_apply_profile_override` (main.py:521-724) consumes it from raw argv BEFORE argparse and strips it, and no subparser claims `-p` (only `_parser.py:23`). Two carve-outs Scarf must never cross: argv after a bare `--`, and the `hermes mcp add … --args <child argv>` passthrough region. Verified writable keys — `model.default`/`model.provider` (same as root), `mcp_servers.<name>.enabled` (a SCALAR, absent ⇒ true), and `tools enable|disable <name> --platform <p>` which writes `platform_toolsets.<platform>` #p0 #verified
- [decision] Per-bot skills enablement ships READ-ONLY, and `canWriteSkillEnablement` states the reason rather than offering a dead toggle. There is no `hermes skills enable/disable` verb at the tag, and `skills.disabled` is a LIST which `hermes config set` cannot express — the root Skills screen has the identical gap. Forking a bespoke YAML list writer the root path would not share was rejected (charter C5 + "prefer reusing an existing surface") #p0
- [gotcha] An existing-but-unreadable `config.yaml` yields the same all-nil snapshot as an ABSENT one, which would render as "running on Hermes' defaults" for a bot that may be pinned to anything. `BotAgentConfig.configReadable`/`isTrustworthy` separate the two — found in the P0 fresh-eyes audit. Same family as the Phase A refuse-degraded-merge-base rule, which P0 also applies to `SOUL.md` at `<profile_dir>/SOUL.md`: an oversized/unreadable file THROWS `unsafeToRead` on both read and write, so a user can never save an empty editor over a real identity prompt #p0 #fixup

## P1 — the bot editor's Agent area (app target)

P1 fills `BotDetailView`'s new third slot, `agent` (the slot grammar is now conversation → agent → automation, each a generic view parameter with a `BotDetailPlaceholder` default). `BotAgentViewModel` + `BotAgentView`, wired at the one `BotsView` call site, memoized per bot in `BotsViewModel.agentCache`.

- [decision] **A write always wins over an in-flight read.** Every mutation (`setModelPin`, `clearModelPin`, `setToolset`, `setMCPServer`, `saveSoul`) bumps a `generation` counter BEFORE it starts, and a load applies its snapshot only if the token it captured is still current. Without it, a snapshot read issued moments before a pin write lands after it and repaints the OLD origin — "I pinned it and it flipped back". Every action then re-reads (`load(force: true)`) regardless of outcome, so a partial pin (provider written, model refused — P0 writes provider first on purpose) shows what actually landed rather than what was asked for #p1 #race
- [decision] **A reload never clobbers a dirty `SOUL.md` buffer, and a save never clobbers an external edit.** `apply(_:)` returns before touching `soulText`/`soulBaseline` while `isSoulDirty` — the unsaved identity prompt is the only state on this surface with no other copy. P0's `writeSoul` re-verifies READABILITY immediately before replacing (Phase A's refuse-degraded discipline) but has no way to know the editor's merge base, so the stale-buffer check has to live in the view model: `saveSoul` re-reads and refuses with a conflict state if the file differs from the baseline, offering "Reload from Disk" (discard) or an explicit "Overwrite". `force` skips only the conflict re-read, never the unreadable/over-limit floor (over-limit AND conflicted is reachable). A small TOCTOU window between that re-read and the transport write is inherent and accepted #p1 #fixup
- [decision] Origin is a typed `ModelPinState` (`unknown` / `unreadable(path:)` / `pinned` / `hermesDefault`), never a string sniff, and `unreadable` is its own case so an existing-but-unparseable `config.yaml` can never render as "Hermes default" (P0's `configReadable` reaching the UI). In that state `canEditConfig` is false and every toggle/pin button is disabled — a write there would be issued blind against a file Scarf never read. A MISSING config is trustworthy and does read as "Hermes default", with copy saying profiles don't inherit the main profile's model #p1
- [fact] Per-bot toolsets are read with `hermes -p <bot> tools list --platform cli`, not from `platform_toolsets.<platform>`: the pinned list only exists once something has been changed, and Hermes computes the effective set at read time (`_get_platform_tools`), so the file alone can't enumerate what the agent loads. `ToolsViewModel`'s private row parser moved to `ScarfCore.HermesToolsList` so both surfaces parse ✓/✗ rows identically #p1
- [decision] Toolsets flip optimistically and snap back on failure (mirroring the root Tools screen); MCP servers do NOT — an MCP row's truth is the parsed `enabled:` key whose ABSENCE means enabled, which only a re-read knows, so the row waits for the snapshot and carries an "on by default" badge. Both surface per-row busy state and the CLI's verbatim text ("Unknown toolset 'x'", "config is managed by /etc/hermes/…") #p1
- [gotcha] `hermes config unset` exits NON-ZERO with "Config key not set" for a key that was never pinned. Clearing a pin fires both `model.default` and `model.provider` unconditionally, so a bot pinned to only one of them would otherwise report a spurious failure — `isBenignUnset` filters those before anything reaches `errorMessage` #p1
- [decision] The model picker is reused unmodified, WITHOUT `onSelectLocal`: that tab writes provider+model+base_url as one payload and P0 has no per-bot `base_url` writer, so offering it would save `model.provider: ollama` with no endpoint and silently route the bot to OpenRouter (the GH #27132 class). A bot that already has `model.base_url` shows the endpoint and says where to edit it instead #p1
- [decision] The unsaved-changes guard lives in `BotsView.requestSelection` — every roster tap (local bot AND remote peer) routes through it, so the two identity spaces stay mutually exclusive in ONE place instead of two hand-written clears. The cached view model means switching away doesn't actually lose the buffer, but the user has no way to know that, so the switch is held for an explicit Discard/Keep Editing #p1
- [fact] Skills ship read-only as P0 promised, with a footnote naming the reason (no CLI verb, `skills.disabled` is a list `config set` can't express) rather than a disabled toggle #p1


## P2 — roster quality + the audit board's perf items (commit f6c0759)

Search, per-bot activity/previews, presence, and A1-M3/M4. New ScarfCore types: `BotsRosterScan`, `BotAvatarCache`, `BotPresence`/`BotActivity`; new entry points on `BotsService`, `SessionPreviewSQL` and `HermesDataService`.

- [decision] **The single-session preview is a narrow entry point over the SAME builders, never a second port.** `SessionPreviewSQL.firstEligibleUserRowSQL(sessionScoped:…)` differs from the list form by exactly `AND m.session_id = ?` and a dropped `GROUP BY` (a bare aggregate returns one row; NULL `min_id` joins to nothing). Eligibility, extraction, the schema-gated active clause and the carrier pre-filter are the identical expressions, so carrier semantics can only ever change in one place. Running the list query per bot would `GROUP BY` the whole `messages` table N times and throw away all but one row each. `fetchBotChatActivity` then reads the **timestamp from the compression chain's live tip and the preview from its origin** — the tip's earliest rows are carriers or mid-conversation turns and would preview as nothing #p2
- [gotcha] **A roster filter must never move the selection.** The first cut retargeted `selectedProfileName` when the selected bot was filtered out — which routes around `BotsView.requestSelection`, the ONE choke point holding a switch when the outgoing bot has unsaved `SOUL.md` edits (P1), and whose `didSet` tears down the live `hermes acp` subprocess. So a keystroke would have killed a conversation and silently discarded an identity prompt. Filtering is now a view of the roster, never a navigation; the detail pane stays on a bot the roster no longer lists #p2 #fixup
- [decision] **The avatar cache is per-connection, never static.** Avatar paths are absolute and NOT unique across hosts (`/home/me/.hermes/profiles/ops/assets/avatar.png` names a different picture on every server), so a process-wide cache would show one host's faces on another after a server switch — same reasoning that keeps `BotsViewModel` free of static state. Keyed by profile+path+size+mtime, and the write path invalidates **explicitly on both outcomes**: a remote `stat` reports mtime in whole seconds, so two writes inside one second at the same byte count collide, and a failed identity-save may still have landed the bytes. The key is the fast path, not the correctness argument #p2 #a1-m4
- [decision] **Batched SSH scan refuses rather than degrades.** One `sh` round trip enumerates `<root>/profiles`, base64s every `profile.yaml` (bounded by `wc -c`, not `stat`, which the per-file path tolerates missing) and stats every avatar; ordering and name validation are computed in Swift on both paths so shell glob order and locale collation never reach the roster. Any doubt — no `base64`/`openssl`, a missing `OK` sentinel, non-zero exit, a lost `default` row — returns nil and falls back to the per-file scan, because quietly reporting "no profile.yaml" would render a configured bot as an unmanaged profile: worse than slow. A `stat` that answers neither GNU nor BSD form still emits the avatar with a degenerate `0 0` key rather than dropping the line, which would be a real divergence. Parity (incl. malformed/oversized/non-UTF-8/empty/absent and a quote in the root path) is pinned against a real `LocalTransport` #p2 #a1-m3
- [fact] **Activity is priced, not hidden.** Per bot on SSH: one batched preflight (`RemoteSQLiteBackend.open` folds sqlite3's version + both `PRAGMA table_info`s into one script) plus title lookup, compression-tip walk, last-message and preview — ~6-7 round trips, so seconds for a 12-bot host. It therefore runs strictly after paint, only for bot-managed profiles, sequentially (twelve concurrent sqlite3 invocations on one ControlMaster channel is worse), and **only on first load or an explicit Reload** — `load(force:)` from a mutation keeps `refreshActivity` false, so pinning a bot does not re-open twelve databases, and cached activity survives the re-scan. Each profile must be opened separately regardless: profiles migrate independently, so schema flags are per-database. "Recent activity" ordering breaks ties with the total pinned-then-name comparator, which is what stops the roster reshuffling while previews land row by row #p2 #c10


## P3 — queued audit-board follow-ups (commit 466bb7f)

Bots/peers-scope items from the pre-release go/no-go board's "queued follow-ups" list (not blocking, but batched into one cycle): A2-F5, A1-L7/L8/L9/L10, A4 (CreateRoutineSheet dynamic type), A1-M2/A2-F7.

- [decision] **Shared `PeersViewModel` is injected, not looked up.** `BotsViewModel` gained `init(…, peers: PeersViewModel? = nil)`; `ContentView` passes `cachedVM(.peers) { PeersViewModel(context: serverContext) }` — the exact same coordinator-cache call the standalone `.peers` case makes — into the `.bots` case's `BotsViewModel` construction. Both resolve through the SAME `AppCoordinator` instance because `ContentView`'s `@Environment(AppCoordinator.self)` is per-window (`ContextBoundRoot` is `.id(context.id)`), so there's no cross-window bleed to guard against — window isolation was already free from t-aud24's cache, this just stopped `BotsViewModel` from opting out of it with its own private `PeersViewModel()`. Tests never pass `peers:`, so they keep building their own isolated instance (the lazy `_peers` fallback in the `peers` computed accessor is unchanged) — no test fixture drift #p3 #a2-f5
- [gotcha] **`routineInputError`'s empty-prompt guard is Scarf's own addition, not Hermes Desktop's.** `cron.tsx:258-268`'s `routineInputError` only checks NUL in title/instruction; it does NOT check emptiness (Hermes Desktop's create sheet disables Create separately on `!title || !schedule`, verified — instruction/prompt has no separate presence check there). `BotRoutinesViewModel.routineInputError` folds both together as one function because Scarf's sheet only had one disabled-check call site to update; if a future audit compares this function's NUL branches against a newer `cron.tsx`, don't expect the empty-prompt branch to have a TS counterpart #p3 #a1-l7
- [decision] **The `isV0206OrLater` mirror moved from a `@ViewBuilder`-body accessor to `onAppear`/`onChange(of: selectedProfileName)`/`onChange(of: hasCronResumeRunNow)`**, exactly mirroring `CronView`'s own three-hook pattern for the same flag. The old comment on `routinesViewModel(for:)` claimed the mutation happened "outside the ViewBuilder closure" — false: the function was called FROM inside `detail`'s `@ViewBuilder` body. `BotsView` now reads `capabilitiesStore?.capabilities.hasCronResumeRunNow` (named capability, `= isV0206OrLater` in `HermesCapabilities`) instead of the raw version check, so a future floor change for Resume & Run Now only has one place to move #p3 #a1-m2 #a2-f7
- [fact] **`avatarTooLarge` surfaces as a per-row triangle, not a global banner.** `fillAvatars` used to be `try? backend.loadAvatar(at: stat)`, which made `BotsError.avatarTooLarge` indistinguishable from "no avatar file" or a transient transport hiccup. It now switches on `Result<HermesBotAvatar, Error>`: `.avatarTooLarge` sets `BotRow.avatarTooLarge = true` (cleared on the next successful read of that key), anything else falls through to the existing silent-fallback behavior. `BotsView`'s roster row shows a small `exclamationmark.triangle.fill` beside the title with `.help(...)` + an accessibility label — no new sheet or alert #p3 #a1-l9
- [decision] **`canSave` in `BotEditorSheet` duplicates `createBot`'s `!= "default"` refusal rather than the view model owning both.** `HermesProfileScope.isValidName("default")` returns `true` (it IS a valid, addressable name — Hermes' own `default` profile satisfies the same character/length rules) so the view model's separate `name != HermesProfileScope.defaultProfileName` guard in `createBot` was never reachable from a disabled button before this fixup. The two checks now live in two places by construction, not oversight: the button-disable is UI-only (never worth threading back through `BotsBackend`), and `createBot` keeps its own guard as defense-in-depth for any future caller that bypasses the sheet #p3 #a1-l10


## P4 — fresh-eyes audit fixups (commit f5b18d4)

Closed the three should-fixes plus cheap nits from the Phase B fresh-eyes audit board pass.

- [decision] **`BotsViewModel.rename` shares `requestSelection`'s unsaved-edits floor, and re-keying isn't safe.** `agentCache`/`routinesCache` are keyed by profile name, so a rename that didn't check `unsavedAgentEdits(forProfile: from)` first would strand a dirty SOUL.md buffer under a name nothing addresses any more — the same guard already blocks a plain roster switch. On success, both caches are **invalidated for the old name, never re-keyed**: `BotAgentViewModel`/`BotRoutinesViewModel` capture their profile name in an immutable `let` used on every backend call, so moving the cached instance to the new dictionary key would leave it silently issuing reads/writes against the profile directory that no longer exists at that path. Invalidating and letting the next `agentViewModel(for:)`/`routinesViewModel(for:)` build fresh is the only safe move — and it's only safe here because the guard above already confirmed there's no unsaved buffer to lose in the drop #p4 #fixup
- [decision] **A `@ViewBuilder` body must never write a stored property, in either capability-mirror helper.** `BotsView.agentViewModel(for:)` had the exact anti-pattern P3 already removed from `routinesViewModel(for:)` — writing `vm.capabilities` from inside the `detail` body, which SwiftUI can re-evaluate for reasons unrelated to a capability change. Fixed the same way: the fetch accessor is pure, and a new `mirrorAgentCapability(forProfile:)` does the write from `.onAppear`/`.onChange(of: hasCronResumeRunNow)`/`.onChange(of: selectedProfileName)`, alongside `mirrorRoutinesCapability`. Both helpers' doc comments now name each other so a future reader sees this is an enforced pair, not one fixed instance #p4 #fixup
