## Artifacts

Diagnosed and closed by P48 (`t-86311c5a`), commit `86b49af1` on `fix/whole-surface-audit-r5`.

**The diagnosis.** Nothing in `ACPClientStartIdempotenceTests` was racy about the client. Every reported failure across rounds 3–5 was `timed out waiting for condition` — the suite's private `waitFor` helper had a **3 s** default ceiling, and on a machine running the other ~3000 ScarfCore tests in parallel, 3 s is easily exceeded by scheduling alone. A ceiling that bounds a HANG was written as if it measured latency. It is 30 s now, with the reasoning in the doc comment; nothing in the suite asserts that the client is fast.

Two aggravating defects found alongside it:

1. **`SpawnLedger.waitForGate()` (`:70-71`) and `GateBoard.arrive()` (`:238-239`) spun forever.** A test whose gate is never opened — because an assertion above it failed and the `openGate()` call was never reached — hung the whole `swift test` run rather than failing, which under parallel load is indistinguishable from the flake itself. Both are bounded at a shared 30 s `gateCeiling` and record an issue.
2. **`concurrentStartsSpawnOneChannel:108` was vacuous.** It slept 50 ms and then asserted "no second channel yet" — which a task the scheduler has not started yet satisfies trivially, so on a loaded machine the check was a statement about the scheduler. It is a latch proving the second task's body actually ran, plus a settle window in which the invariant is CHECKED repeatedly rather than sampled once; the load-bearing proof remains the `ledger.count == 1` after both starts complete.

Verified: `--filter ACPClientStartIdempotenceTests` 5/5, and two full `swift test` runs (3038 tests / 233 suites) green with no reruns needed — this suite did not appear in either.
