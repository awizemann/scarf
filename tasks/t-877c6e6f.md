**Product bugs found and filed (not fixed here)**
- **t-ec6d2e6d (high)** — Skills → Uninstall never uninstalls and reports success. `SkillsView` passes `skill.id` (`<category>/<name>`, from `SkillsScanner.swift:71`) where the CLI wants the bare name, AND the CLI's rejection exits 0 so the exit-code check reads success. Verified against the installed v0.21 CLI. The regression test is wrapped in `XCTExpectFailure` naming the task, so it keeps the gate green while open and fails as soon as the bug is fixed.
- **t-42c56c2f (low)** — XCUITest cannot move a SwiftUI segmented Picker's selection, so `SkillsView`'s tab strip is undrivable (SettingsView's button strip is fine). The hub-install journey skips naming this task.
- **t-e3926f86 (medium)** — UI gate stabilization: infrastructure-class failures on a loaded Mac (event-synthesis timeouts, lost app connection).

**Not done / deviations**

The journey exists, probes the hub with a 5 s timeout, and currently always skips on t-42c56c2f.
- **The Models-section preset journey has not run to completion on this host** — the `Models` sidebar row is capability-gated and did not appear against an isolated home even on a v0.21 host (the existing section sweep already marks Models `gated: true`). The journey is written and skips cleanly; it needs a host where the row renders.
- **Journey 2 was split.** The brief asked to switch the model in the Models section and assert config.yaml. The Models section does not write config.yaml — it is the preset overlay at `scarf/model_presets.json`. So the config.yaml switch goes through Settings → General → Model (where that write actually lives) and the Models section gets its own journey against the preset store.
- **No base-class change was needed for the relaunch:** `isolatedHome` outlives a `gracefulQuit`, so a second `makeApp()` in the same test method is already pinned to the same home.
