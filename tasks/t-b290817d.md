## Description

Follow-on from P56 (round-6 decision 6, `t-19ba24a5`), which gave the Kanban Review column its two exits.

`KanbanService.reopenReview(taskIds:reason:)` accepts a `--reason`, and `_cmd_reopen_review` records it as a `CHANGES REQUESTED: <reason>` comment on the task before reopening (`hermes_cli/kanban.py:990-1008` @ `v2026.9.7`, via `kb.add_comment`). The DRAG path deliberately sends `reason: nil`: a drag carries no text, and inventing a reason on the reviewer's behalf would put words in a review they did not write.

But a reviewer sending work back almost always has one, and today they have to reopen the card and then add a comment separately. The shape already exists on this board: `KanbanBlockReasonSheet` is presented from `handleDrop`'s `.blocked` arm and its text is threaded through `attemptMove(blockReason:)`.

Scope:
- A reason sheet on the `review -> upNext` drop, in the `KanbanBlockReasonSheet` shape (optional text, not required — an empty reason must still reopen).
- Thread it through `attemptMove` the way `blockReason` / `completeResult` already are, into `applyStep`'s `.reopenReview` arm.
- Gate with the same `HermesCapabilities.hasKanbanReviewExits` (v0.20.1) the transition itself is gated on; `--reason` is on the verb at its first tag (`hermes_cli/kanban_parser.py:323-326`), so it needs no flag of its own.
- Also worth considering for the same sheet: `review -> done` is a human APPROVAL, and `kanban complete --result` already has a sheet (`KanbanCompleteResultSheet`) that `handleDrop` offers only when the source is `running`. A review card gets none today.
