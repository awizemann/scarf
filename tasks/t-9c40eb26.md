## Description

Deferred from S2 (t-a2c169f0), audit LOW "TOCTOU on containment checks".

S1's `PathGuard` (scarf/scarf/Core/Services/ProjectTemplateUninstaller.swift:508+) re-derives containment at PLAN time and again at TIME OF USE inside `uninstall(plan:)`, and `removeRecursively` re-checks every child and unlinks symlinks instead of descending. S2 verified that and extended the same discipline to the project-dir removal (`removeProjectDirIfEmpty` now lists the directory again rather than trusting the plan's `projectDirBecomesEmpty` flag).

What is left is the irreducible window between `guardian.admits(path)` and `transport.removeFile(path)`: an attacker who can swap a component for a symlink inside that window still wins. Closing it needs a filesystem primitive `ServerTransport` does not expose — `openat`/`O_NOFOLLOW`-style operations, or an `unlinkat` with a directory fd — and adding one means designing its remote (SSH/SFTP) counterpart, where there is no fd to hold.

Deferred because: the window requires local write access to the project tree AND precise timing against a user click, the surviving exposure is bounded by the lexical containment check (the attacker can only redirect INSIDE a path that still standardizes below the project root), and the fix is a transport-protocol change rather than a call-site change.

Suggested scope: design `ServerTransport.removeFileNoFollow(_:relativeTo:)` (local: `unlinkat` with `AT_SYMLINK_NOFOLLOW` against a held dirfd; remote: document as best-effort lexical, matching how `PathGuard` already degrades remotely), then route the uninstaller's deletions through it.
