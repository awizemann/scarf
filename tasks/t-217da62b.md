## Description

Fix-1 audit finding (pre-existing, report-only). ACPClient.resumeSession (ACPClient.swift:351-370) requires a top-level sessionId in the session/resume response, but the ACP schema's ResumeSessionResponse has no such field (only _meta/configOptions/models/modes) — so on Hermes 0.15+ resume always throws "Missing sessionId" and falls back to loadSession: resume is dead code in practice. Worse: Hermes's resume_session CREATES a new session when the id isn't found, so each reconnect attempt against a not-restorable id orphans one server-side session (up to maxReconnectAttempts=5 per episode). The real id lives in _meta.hermes.sessionProvenance. Needs design: either parse the _meta provenance id and make resume real, or drop resume from the reconnect ladder entirely (load-only) and avoid the orphan-creation side effect. Both Mac attemptReconnect (~ChatViewModel:1475) and iOS ChatView.swift:2082 share the ladder.

## Plan

Design decision (source-verified, 0.17 tree + v2026.7.7.2 tag): DROP session/resume from both reconnect ladders rather than parse _meta provenance — resume restores through the identical server path as load (update_cwd → get_session) but silently creates an orphan session on unknown ids, and its success response is top-level indistinguishable from an orphan-create (provenance meta is best-effort/None-able → phantom-session risk). Load fails detectably ({}). Deleted ACPClient.resumeSession (dead code — required a top-level sessionId ResumeSessionResponse never carries); Mac attemptReconnect + iOS ChatController ladder + iOS open-session path are load-only. Also (scope B, from t-fd61272d): ACPError decodes error.data, .rpcError carries details, errorDescription leads with truncated details (detailsLead: first line/sentence, 200-char cap), full text to os Logger.
