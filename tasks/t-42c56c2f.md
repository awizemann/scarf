## Description

Found while building the UI-gate P2c config journeys (t-877c6e6f).

`SkillsView.modePicker` is a `Picker(...).pickerStyle(.segmented)` (Installed / Bundles / Browse Hub / Updates). **XCUITest cannot move its selection.** Verified on macOS 26 with the real app: the segments do surface in the accessibility tree as `RadioButton`s with correct labels and values —

    RadioGroup, identifier: 'Skills.root'
      RadioButton, label: 'Installed',   value: 1
      RadioButton, label: 'Browse Hub',  value: 0
      RadioButton, label: 'Updates',     value: 0

— and `.click()` on the Browse Hub segment reports success but the binding never changes. Retried three times, located both by label and by index, with the app confirmed frontmost. A SwiftUI `.accessibilityIdentifier` on the `Picker` does not reach the AppKit-synthesized segments either (it propagates the section's `Skills.root` down instead), so there is no identifier to target.

`SettingsView.tabStrip` has the same shape of problem solved correctly: it is a row of real `Button`s, each carrying `settings.tab.<rawValue>`, and the journeys drive it without trouble.

**Ask:** give `SkillsView`'s tab strip the same treatment — a `Button` per visible tab with `skills.tab.<rawValue>`. Keep the visual segmented appearance; only the underlying control changes. The existing `skills.tabPicker` identifier can go.

**Unblocks:** `testInstallSkillFromHub` in `scarf/scarfUITests/ConfigJourneyUITests.swift`, which currently `XCTSkip`s with a message naming this task because it cannot reach the Browse Hub tab. (That journey is also network-gated by design — SkillsView has no offline install path — so it stays opt-in either way.)
