## Description

Deferred from D2 (t-a2c169f0). Listed in the D2 ticket's description but outside the scope the execution brief set, so it was NOT touched — flagging rather than dropping it.

From the P7 data-integrity audit (documents/reports/2026-09-03-projects-full-surface-audit.md, C2): `session_project_map.json` is the SOLE record of session-to-project attribution, and it grows without bound — one entry per session, forever. D1 gave it the `GuardedJSONStore` treatment (salvage / quarantine / refusal / `.bak`), so a read failure no longer destroys it, and bytes past the cap are now quarantined rather than decoded. That converts silent truncation into a visible quarantine, which is strictly better and is why this is medium rather than high.

What is still true: growth is monotonic, the cap is a real ceiling a long-lived install will reach, and reaching it means the whole attribution index is set aside at once (every session loses its project). iOS over SFTP is the likeliest first casualty.

Suggested scope: prune entries whose session no longer exists in `state.db` (read-only, charter C3) on a cadence that is NOT the watcher tick; keep a bounded most-recent tail as the floor so a state.db Scarf could not read never empties the map; test that a prune pass with an unreadable state.db writes nothing.

## Artifacts

**Verified, with one real gap found and closed.**

Finding: pruning already fired on the write path for BOTH writers. `ChatViewModel` (Mac) and `Scarf iOS/Chat/ChatView.swift` are the only non-test callers of `attribute`, and every write verb (`attribute`, `forget`) funnels through `SessionAttributionService.mutate` → `mutateLocked`, which calls `SessionProjectMap.prune()` before encoding. The service was promoted to ScarfCore in M9 #4.2 precisely so Mac and iOS share one path; there is no second writer of the file in the app.

Gap closed: the idempotent early-return (`attribute` of a session already pointing at the same project reports "no change") returned BEFORE the prune. An install that only ever re-attributes sessions it already knows — every resume of an existing project chat — would never trim an over-cap file inherited from an older Scarf or another device. `mutateLocked` now evaluates the prune regardless and writes when either the body OR the prune changed something; an under-cap, unchanged map still writes nothing.

Files:
- `scarf/Packages/ScarfCore/Sources/ScarfCore/Services/SessionAttributionService.swift` — prune runs on every write path.

Not fixed, recorded in memory: `SessionProjectMap.extra` (unknown top-level keys carried verbatim) is not bounded by pruning, so an agent-written blob can still push the file over the cap with 2000 legitimate mappings.
