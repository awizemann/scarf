## Description

From documents/hermes-v0.21.1-whole-surface-audit.md (class 3, charter C10). Brief: documents/hermes-v0.21.1-parity-agent-brief.md. The app target is MainActor-isolated by default (project.pbxproj SWIFT_DEFAULT_ACTOR_ISOLATION), and `ServerContext.runHermes` is synchronous with a 60 s default timeout.
1. SettingsViewModel.swift:167-190 `applyConfigWrite` (every scalar toggle/stepper/picker in every Settings tab) runs `runHermes` + `fileService.loadConfig()` synchronously on the main actor; :561-579 setMemoryProvider off-branch; :987-996 runConfigCheck/runConfigMigrate; AdvancedTab.swift:161-169 calls them from a Button action. Move all to the `Task.detached { … } → MainActor.run` hop the file already uses for load()/applyModelPickerSelection/bitwardenStatus/saveDirectYAML. Keep write ordering (serialise writes so two quick toggles don't race the re-read); also refresh rawConfigYAML + personalities after a write (SettingsViewModel.swift:175, LOW finding).
2. GatewayView.swift:53 `.onChange(of: fileWatcher.lastChangeDate) { viewModel.load() }` + GatewayViewModel.swift:114-137: no change-token, no cancellation; each gateway_state.json rewrite spawns `gateway status`, `pairing list`, `gateway list`. Adopt the PlatformsViewModel.load(changeToken:force:) pattern and cap the runHermes calls with explicit timeouts.
Tests: a fake context whose runHermes sleeps must not block a main-actor assertion; coalescing test that N rapid ticks produce one in-flight load. Read memory `conventions/a-mainactor-suite-cannot-test-detached-read-interleaving` first.

## Artifacts

Shipped in commit `79a6331a` on `fix/whole-surface-audit` (6 files, +493/-57).

**1. SettingsViewModel — writes off the main actor, serialised**
- New `HermesCLIRunner` seam (`scarf/scarf/Core/Models/HermesCLIRunner.swift`) + `ServerContext.cliRunner`. `ServerContext` is a Sendable struct with a concrete `runHermes` extension, so there was no protocol/subclass to substitute; both VMs now take an optional `cliRunner` init parameter.
- `applyConfigWrite` → `enqueueConfigWrite` + `commitConfigWrite`: `Task.detached` for the spawn AND for the config re-read, main-actor tail for analytics/state/banner. Serialised behind `writeChain` (each write awaits the previous) so two quick toggles cannot interleave a write with another write's re-read.
- `setMemoryProvider("")` (`hermes memory off`) now rides the same chain.
- `runConfigCheck()` / `runConfigMigrate()` are now `async`; `AdvancedTab` buttons show "Running…" immediately and fill in from a `Task`. `runConfigMigrate` joins `writeChain` (it rewrites config.yaml).
- LOW finding: a successful write now refreshes `rawConfigYAML` and `personalities` too (both derived from config.yaml, previously stale until manual Reload).
- Dead private `runHermes(_:)` removed. Behaviour preserved exactly on the failure path (no config re-read on a refused write, as before).

**2. GatewayViewModel — change-token coalescing + explicit timeouts**
- `load(changeToken:force:)` mirroring `PlatformsViewModel`: `hasLoaded` / `loadedChangeToken` / `inFlightChangeToken`, cancel-prior `loadTask`, `Task.isCancelled` checks between the three probes, existing `loadGeneration` guard kept.
- `GatewayView.onChange(of: fileWatcher.lastChangeDate)` passes the token.
- `probeTimeout = 30` passed explicitly to `gateway status` and `pairing list` (was the silent 60 s default).
- `force: true` on section re-entry (onAppear) and on every post-mutation reload (start/stop/restart, approve, revoke) — `gateway status` is a live liveness probe and the gateway can die without rewriting `gateway_state.json`, so those must never coalesce away.

**Tests** — `scarf/scarfTests/MainActorBlockingWritesP11Tests.swift`, 7 tests:
`settingsWriteDoesNotBlockTheMainActor`, `memoryProviderOffDoesNotBlockTheMainActor`, `rapidTogglesAreSerialised`, `configDiagnosticsRunOffTheMainActor`, `successfulWriteRefreshesRawYAMLAndPersonalities`, `rapidTicksProduceOneGatewayLoad`, `gatewayLoadDoesNotBlockTheMainActor`.

Fix-removal verified for every one of them (each fails with its fix reverted). Two honesty corrections during authoring, both recorded in memory:
- Measuring the elapsed time of the synchronous `vm.setSetting(...)` call proves nothing — the `Task { }` body on a MainActor class cannot start until the caller returns. Both timing tests passed with the detached hop deleted.
- The replacement (repeated `Task.yield()` main-actor latency) *did* fail correctly in isolation but flaked under the full parallel `scarfTests` run. Final form asserts `Thread.isMainThread` recorded inside the fake runner — deterministic.

**Test results**: ScarfCore `swift test` 2425 tests / 159 suites passed. App target `scarfTests` 874 tests / 114 suites passed. One unrelated flake on the first full run (`BotConversationTests` "a real session/load failure drives the fallback into verifyCanonicalBinding"); passed in isolation and on the clean re-run. `xcodebuild build` succeeds.

**Fresh-eyes findings on my own diff, fixed before commit**: adopting the Platforms coalescing pattern verbatim would have made Gateway section re-entry skip the live `gateway status` probe (Platforms reads files only, Gateway probes a process) — changed onAppear to `force: true`. Also `rapidTogglesAreSerialised` initially compared against a span whose exit stamp was still its placeholder entry stamp, making the overlap check vacuously true; it now waits for both invocations to complete.

**Disputed findings**: none. **Deliberate no-ops**: `SettingsViewModel.configCommandTimeout` is 60 s, the same value `runHermes` already defaulted to — named rather than lowered, because shortening a config-write cap risks a C1 pre-target degradation for no audit-visible gain. The gateway probes were lowered to 30 s because they are sub-second status reads and the finding is specifically about ticks piling up behind a wedged host.
