## Description

From documents/hermes-v0.21.1-whole-surface-audit.md (class 3, charter C10). Brief: documents/hermes-v0.21.1-parity-agent-brief.md. The app target is MainActor-isolated by default (project.pbxproj SWIFT_DEFAULT_ACTOR_ISOLATION), and `ServerContext.runHermes` is synchronous with a 60 s default timeout.
1. SettingsViewModel.swift:167-190 `applyConfigWrite` (every scalar toggle/stepper/picker in every Settings tab) runs `runHermes` + `fileService.loadConfig()` synchronously on the main actor; :561-579 setMemoryProvider off-branch; :987-996 runConfigCheck/runConfigMigrate; AdvancedTab.swift:161-169 calls them from a Button action. Move all to the `Task.detached { … } → MainActor.run` hop the file already uses for load()/applyModelPickerSelection/bitwardenStatus/saveDirectYAML. Keep write ordering (serialise writes so two quick toggles don't race the re-read); also refresh rawConfigYAML + personalities after a write (SettingsViewModel.swift:175, LOW finding).
2. GatewayView.swift:53 `.onChange(of: fileWatcher.lastChangeDate) { viewModel.load() }` + GatewayViewModel.swift:114-137: no change-token, no cancellation; each gateway_state.json rewrite spawns `gateway status`, `pairing list`, `gateway list`. Adopt the PlatformsViewModel.load(changeToken:force:) pattern and cap the runHermes calls with explicit timeouts.
Tests: a fake context whose runHermes sleeps must not block a main-actor assertion; coalescing test that N rapid ticks produce one in-flight load. Read memory `conventions/a-mainactor-suite-cannot-test-detached-read-interleaving` first.
