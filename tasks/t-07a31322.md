## Shipped

1. **HIGH — cron `Repeat` clear.** `CronViewModel.repeatEditArguments(existing:newValue:)` emits `--repeat 0` (which `normalize_repeat_value` folds to `None` = forever) only when the seeded value was non-empty and the user emptied it. Floor-walked across all 32 `v2026.*` tags: `cron edit --repeat` is registered at `hermes_cli/main.py:3946` at `v2026.3.30` = **v0.6.0** (Scarf's minimum), and the `<= 0 -> forever` fold at `cron/jobs.py` from `v2026.3.23` = v0.4.0 — both BELOW the floor, so **no capability flag** (C1 satisfied by absence of a rejecting host generation).
2. **MED — cron `Prompt` clear.** `promptEditArguments` emits `--prompt ""` on the same seeded-vs-emptied rule. Guard verified in BOTH emitters: `hermes_cli/cron.py::cron_edit:621` passes `getattr(args, "prompt", None)` straight through, and `tools/cronjob_tools.py::_update_core_fields:689` is `if prompt is not None`. Legality per job kind is left to Hermes: `job_payload_is_empty` (`cron/jobs.py:428-436`, armed at :1949) refuses a job left with no runnable payload, and that sentence is surfaced verbatim rather than duplicated client-side. `CronView` now passes `existingPrompt:` / `existingRepeatCount:` (both REQUIRED params, no defaults, so a future caller cannot silently reinstate the bug).
3. **MED — cold-launch doctor re-parse.** `loadDoctor` retains the run's raw stdout and parses on the main actor against the CURRENT roster (was: a snapshot taken before the hop); `load()` calls the new no-spawn `reparseDoctorFindings()` on every roster change. Whichever of `load()`/`loadDoctor()` finishes second now re-keys the findings. The old gated re-RUN is KEPT (still `if hasLoadedDoctorFindings`) so an external `jobs.json` edit still refreshes genuinely-stale findings. C1: the re-parse provably adds no spawn on any host.
4. **MED — `isLoadingDoctor` early-return hole.** `loadDoctor`/`loadIncidents` now coalesce a dropped `force` call via a `pending` flag and re-issue once on completion, and `refreshDiagnosticsAfterMutation` gates on `hasLoadedX || isLoadingX` — a probe in flight is a probe this host already received, so no pre-target host gains a spawn.
5. **MED — `oneShotIsUnresumable`.** The `lastRunAt` arm is replaced by `isTerminal`. Evidence: `resume_job` (`cron/jobs.py:1991`) calls `compute_next_run(job["schedule"])` with `last_run_at` at its `None` default (:1096), so `_recoverable_oneshot_run_at`'s already-run arm (:846) never fires on that path; `rearm_oneshot` (:2036-2055) clears `repeat.completed`/`run_claim`/`fire_claim` but not `last_run_at`. The refusal Hermes actually raises is `_reject_terminal_activation` (:1865-1878), and `_advance_after_run` retires every spent `kind == "once"` via `_complete_job_record`, so the guard did not get weaker. `IOSCronViewModel.oneShotRefusalMessage` re-keyed to the same predicate.
6. **MED — `FleetApplyExecutor.cronFieldStatus`.** Now takes `cancelledRemaining`; `failed > 0` is `.failed` regardless of `created`, and `created == 0` with either script-only skips or cancellation is `.skipped`. Matches the existing between-targets behaviour (`.skipped "cancelled before apply"`, :153).
7. **MED — `boolOpt`.** DELETED; `checkpoints.enabled` reads `boolishOpt`, which now delegates to the new single helper `HermesYAML.boolishValue` (`_TRUTHY_STRINGS`/`_FALSY_STRINGS`, `gateway/config.py:25-32`). The false header comment is now true because the reader it denied no longer exists.
8. **MED — `ProfileRoutesYAML.parseMultiplex`.** Routes through `HermesYAML.boolishValue`, defaulting `false` per `_coerce_bool(multiplex_profiles, False)` (`gateway/config.py:733`, dataclass default :561).
9. **LOW ×2 — ten dead wire keys.** Deleted `HermesKanbanTaskDetail.parentResults`; `HermesKanbanTask.idempotencyKey/lastHeartbeatAt/maxRuntimeSeconds/currentRunId`; `HermesKanbanRun.taskId/claimLock/claimExpires/maxRuntimeSeconds/lastHeartbeatAt/failureCount`. Proof for each: every kanban task dict goes through the single serialiser `_task_to_dict` over `_TASK_DICT_FIELDS`, runs through `_obj_dict` over `_SHOW_RUN_FIELDS`/`_RUNS_RUN_FIELDS` (`hermes_cli/kanban_output.py:18-32`), and the envelope at `kanban.py:492-498` — walked back across the tags (a dict literal before the v0.17 output-module split) with no emitter at any of them. `parent_results` exists only as `kanban_db.parent_results:4060` feeding `_ctx_parent_results:3692` (worker context text, never JSON). Repo-wide grep confirmed no Swift consumer of any of the ten. The doc claims that asserted otherwise ("v2.7.5 fields exposed by `kanban show --json` and `kanban watch`", "parent results") are corrected.
