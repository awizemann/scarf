## Description

Found while doing P21 (round-2 whole-surface audit), out of that phase's scope.

`scarf/scarf/Features/CredentialPools/ViewModels/OAuthFlowController.swift:145-151` has the exact drain race P21 fixed in `MCPLoginController`: the termination handler nils `outPipe.fileHandleForReading.readabilityHandler` and calls `handleTermination(exitCode:)` immediately, with no guarantee the reader consumed the last chunk.

Here the verdict is `succeeded = exitCode == 0 && !outputFailed` (`:233-253`), so the race fails in the OPPOSITE direction from the `mcp login` one: a failure marker (`did not return credentials`, `Token exchange failed`, `OAuth login failed`, `HTTP Error`) written just before `hermes auth add` exits can be missed, and a failed pooled-credential login is then reported as a success.

Fix shape: the same one P21 landed — a lock-guarded inbox on the reader side, an `OutputInbox`-style hand-off, and a `pump()` that judges only once the reader reported EOF AND the exit status arrived (plus a grace deadline so a lingering pipe holder cannot hang the sheet). See `scarf/scarf/Features/MCPServers/ViewModels/MCPLoginController.swift` (`pump`, `scheduleDrainDeadline`, `OutputInbox`) and its `ProcessFactory` injection, which is what made the interleaving testable (`scarf/scarfTests/AuditP21VerdictTests.swift`).

Also worth checking for the same shape: `scarf/scarf/Core/Services/NousAuthFlow.swift:118`, `scarf/scarf/Core/Services/SpotifyAuthFlow.swift:109`, `scarf/scarf/Core/Services/HermesProxyService.swift:102`.
