## Description

Alan gets a permission prompt per edit in project chats (Hermes session mode defaults to 'default'). Build: (1) per-project setting "auto-accept edits" — Scarf sends session/set_mode accept_edits at chat-session start for chats bound to that project (Mac + iOS parity where the mode plumbing exists); (2) a third action on the tool-approval prompt, "Allow edits for this session", which approves the pending request AND flips the session mode to accept_edits. Enforcement stays Hermes-side (sensitive paths still prompt). Also sync the optimistic mode chip when Scarf itself sets the mode.

## Plan

Done. Setting stored Scarf-side (UserDefaults + MiniAppGrantSigner HMAC, reusing the mini-app machine key — never `.scarf/` or the registry, which the agent can write). Session-boot `set_mode accept_edits` on all three session-establishing paths, gated on `hasSessionEditAutoApproval` (v0.15+). Third dialog button offered only for `kind == "edit"` requests carrying exactly one affirmative allow option.

## iOS disposition

NOT built. `Scarf iOS/` has zero approval-mode plumbing — no `setSessionMode` call, no mode picker, no `activeApprovalMode` mirror (grep over `Scarf iOS/` + `Packages/ScarfIOS/Sources` returns nothing). Per the brief, no new wire code was added there. iOS keeps its existing `PermissionSheet` unchanged. Adding parity means first porting the mode RPC + chip to iOS — worth its own task.

## Residual (documented, not fixed)

- The signed record binds the project PATH, not a project identity — same residual `ImageHostConsentStore` carries; payload is composed so a uuid can replace it without a format change.
- On autostart/reconnect the project's posture is re-asserted unconditionally. If the user had manually moved the session OFF `accept_edits` mid-chat, a reconnect puts it back. The mirror can't distinguish "reset to default" from "user chose default", so this was left rather than guessed at.
