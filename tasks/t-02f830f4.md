## Description

Round-5 P48 (decision 5) made `ServerTransport.runProcess`'s `timeout` non-optional and moved both Mac conformers' internal waits onto `Process.waitDraining` / the async twins, and it moved the app target's six `Task.detached` sites onto `waitDrainingAsync`. What it did NOT do is make the SEAM async.

`runProcess` is still `nonisolated func runProcess(...) throws -> ProcessResult` (`scarf/Packages/ScarfCore/Sources/ScarfCore/Transport/ServerTransport.swift:67`). `LocalTransport.runProcess` (`Transport/LocalTransport.swift:260`) ends in a synchronous `proc.waitDraining(timeout:drain:)`, which is a `Thread.sleep` poll loop; `SSHTransport.runLocal` (`Transport/SSHTransport.swift:1047`) ends in a `DispatchGroup.wait(timeout:)`. Both block whichever thread the caller is on — and many callers are `async` (e.g. `SkillsViewModel`, `CuratorService`, `KanbanService`, `HermesVersionCache`, `BotsService`, the iOS views), so they park a cooperative-pool thread for the whole budget. That is the hazard `Process.waitDrainingAsync` exists to remove, one indirection out from the transport.

`ProcessAsyncWaitP43cTests` was widened in P48 to follow ONE level of synchronous indirection within a file, which is why this is visible at all; it cannot follow the call across files, so nothing currently fails.

The fix is to make `runProcess` (and `streamScript`, if it has the same shape) `async throws` on the protocol, both Mac conformers, `CitadelServerTransport` (already async underneath — it wraps `runSync`, which this would delete) and every test double, then `await` at roughly 50 call sites across `scarf/scarf`, `scarf/Packages/ScarfCore/Sources`, `scarf/Scarf iOS` and the test targets. Several call sites are inside synchronous helpers that would become async in turn.

Deliberately deferred from P48 as out of proportion to that phase's named scope; filed here with the reasoning so it is a decision rather than an omission.

## The iOS half (added round-6 P53)

`CitadelServerTransport.runSync` (`scarf/Packages/ScarfIOS/Sources/ScarfIOS/CitadelServerTransport.swift`) is the worst instance of this seam and the one P53 patched rather than removed. It runs the async op on a `Task.detached` — a COOPERATIVE-POOL task — while the calling thread blocks on a `DispatchSemaphore`. If the caller is itself on a pool thread, the two compete for the same fixed set of threads; and the wait had no deadline at all, so a half-open TCP connection with no keepalive stalled both sides permanently.

P53 gave the wait a ceiling derived from the caller's own budget (`runSync(deadline:)`; `runProcess` passes `timeout + syncGrace`, the eight SFTP verbs pass the named `sftpCeiling` because `ServerTransport`'s file verbs carry no caller budget), and wrote the abandonment contract down: on expiry the detached task keeps running and writes into a `ResultBox` nobody reads — the result is dropped, never the work.

**What this task must still do here:** delete `runSync` outright. Once `runProcess` and the file verbs are `async`, the semaphore bridge, the `ResultBox`, `syncGrace` and `sftpCeiling` all go with it, and the eight SFTP call sites stop needing a ceiling invented for them. `CitadelTransportP53Tests` in `scarf/Packages/ScarfIOS/Tests/ScarfIOSTests` pins the bounded bridge; those assertions are expected to be DELETED by this task, not satisfied by it.

P53 also added `scarf/Packages/ScarfIOS/Sources/ScarfIOS` to all three C10 sweep roots (`MainActorSpawnDisciplineP22Tests.sweepRoots`, `ProcessAsyncWaitP43cTests.sweepRoots`, `OffPoolDisciplineP52Tests.roots`), each with its own floor — it had been in none of them, which is how this sat unseen for five rounds.

**Round-6 P58 (decision 11) did the iOS half of the SEAM, and `runSync` is still here.**

Commit `769b6c98` on `fix/whole-surface-audit-r6` added
`ServerTransport.asyncRunProcess(executable:args:stdin:timeout:)` and moved the ELEVEN iOS call
sites onto it (P58b measured it: `git diff 8dc79784..b26c0a1f | grep -c '^-.*runProcess('` = 11;
the note first said twelve). `CitadelServerTransport` OVERRIDES it with its own `async` exec, so
the iOS `runProcess` path no longer goes through the semaphore bridge at all — that part of this
ticket is done, and `CitadelTransportP53Tests`' assertions about `runProcess`'s use of
`runSync(deadline:)` were kept rather than deleted because the synchronous `runProcess`
conformance still exists (it is the protocol requirement) — and P58b found that conformance still
has a LIVE iOS caller: `ServerContext.UserHomeCache.probe` (`ServerContext.swift:343`), unguarded
ScarfCore compiled for iOS, reaching this transport through `ServerContext.sshTransportFactory`.
So `runSync` has **eight** callers, not seven, and converting that probe belongs to this ticket.

**What is left here, restated against the new shape:**

1. The two Mac transports still have synchronous internals. `asyncRunProcess`'s DEFAULT
   implementation (`ServerTransport.swift`) wraps the synchronous `runProcess` in `OffPool.run`, so
   the wait no longer holds a cooperative-pool thread — but it holds a thread. Converting
   `LocalTransport.runProcess` / `SSHTransport.runLocal` to be `async` end-to-end deletes that
   wrapper.
2. **`runSync` survives for the seven SFTP file verbs** (`readFile`, `unguardedWriteFile`,
   `fileExists`, `stat`, `listDirectory`, `createDirectory`, `removeFile`), whose `ServerTransport`
   signatures are still synchronous, **and for the synchronous `runProcess`** while
   `ServerContext.UserHomeCache.probe` still calls it. Making the FILE verbs async plus converting
   that one probe is now the whole of the iOS half, and it is what finally deletes `runSync`,
   `ResultBox`, `syncGrace` and `sftpCeiling`. `ProfilesView.loadHostActiveProfile` shows the cost
   today: it awaits `asyncRunProcess` and then needs a separate `OffPool.run { ctx.readText(…) }`
   beside it, because one verb is async and its neighbour is not.
3. `streamScript` is already `async`; no work there.

**Lesson from doing the iOS half.** Converting a private helper cascades: `SkillsViewModel`'s two
private runners and `CuratorViewModel.runHermes` each made their 9, 1 and 1 callers async in turn,
and `IOSCronViewModel`/`ProfilesView` had to swap `await Task.detached { … }.value` for an
immediately-invoked `{ () async -> T in … }()` because the body was no longer synchronous. The
compiler drives all of it; budget the call-site churn, not the design.
