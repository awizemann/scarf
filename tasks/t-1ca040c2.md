## Description

Follow-up to t-2d39ff83 (v0.21.1 finding B4), deliberately out of that task's scope.

`KnownPlatforms.all` now surfaces dingtalk, sms, irc, wecom, weixin, qqbot, msgraph_webhook, api_server and photon (`scarf/Packages/ScarfCore/Sources/ScarfCore/Models/HermesTool.swift`). None has a per-field setup view, so all nine fall to `PlatformsView.platformForm`'s `default` arm ("No setup form for this platform yet") at `scarf/scarf/Features/Platforms/Views/PlatformsView.swift:190-194` — the same degradation `buzz` has had since v0.20. They are also absent from `PlatformsViewModel.identifyingEnvVar(for:)` (`scarf/scarf/Features/Platforms/ViewModels/PlatformsViewModel.swift:140-146`), so their "Configured" state is detected only from a top-level `<platform>:` block in config.yaml, never from a set credential env var.

Work, roughly in value order:
1. Add `identifyingEnvVar` entries for the ones with an obvious primary credential (verify each against the adapter at tag v2026.9.7 before writing it): irc, sms, wecom, weixin, qqbot, photon (`PHOTON_PROJECT_ID`), api_server, msgraph_webhook, dingtalk.
2. Add real setup views for the highest-value ones. dingtalk is the only one with a destination allowlist (`allowed_chats`) and already has a `GatewayAllowlistKind` mapping, so it is the natural first: a form plus a `GatewayBehaviorSection(platform: "dingtalk", …)` gets the allowlist editor for free.
3. The user-allowlist platforms (`allowed_users` / `allow_from`) have no editor at all today — consider a shared "allowed senders" component rather than one per platform.

Charter: verify every env var and config key against `git -C ~/.hermes/hermes-agent show v2026.9.7:<path>` (C2); these platforms exist at every supported Hermes version, so nothing here is capability-gated.
