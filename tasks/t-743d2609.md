## Description

P5 deferral RESOLVED (2026-09-04). project_set_config shipped as a 7th scarf-projects MCP tool. Investigated reachability: ProjectConfigService/TemplateConfigSchema genuinely can't be linked into ScarfProjectsMCPKit (app target can't be a package dependency — wrong direction). Instead of refusing secrets, LIFTED the actual Keychain code (ProjectConfigKeychain, TemplateKeychainRef, a new TemplateSlug.derive helper) out of the app target into ScarfCore/Services/ProjectConfigKeychain.swift as public types; the app target's originals are now typealiases pointing back at ScarfCore, so there is exactly one implementation. The tool mints/resolves the same com.scarf.template.<slug> project-bound refs (per commit 926452a's namespacing) through the same SecItem* calls the Configuration UI uses — never reimplemented. Secret-ness is decided by the caller's `secret:` argument, cross-checked against the project's cached .scarf/manifest.json schema (read as raw JSON, no dependency on app-only manifest types) when one exists; a schema-less project trusts the caller's flag. A plaintext keychain:// value in `value` is always refused regardless of the flag — refs are only ever minted inside the tool.

Verified: `swift build` and `swift test` clean (1998 ScarfCore tests + 38 ScarfProjectsMCPKit tests, including a real Keychain roundtrip test for the secret path), and the full Xcode app target builds successfully with the new typealiases. Memory note scarf/architecture/scarf-projects-mcp-server-bundled-helper-scarfcore-services updated to reflect the shipped design (was stale, said "DROPPED").
