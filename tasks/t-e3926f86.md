## Description

Raised from t-877c6e6f (UI gate P2c). `ConfigJourneyUITests` passes cleanly — verified green both WITH and WITHOUT the seeded fixture — but not on every run. On a Mac already loaded by repeated `xcodebuild test` cycles the same binary that was green minutes earlier produces infrastructure-level failures:

- `Failed to synthesize event: Timed out while synthesizing event`
- `Failed to get matching snapshots: Lost connection to the application (pid …)` — the app under test actually dying
- the app losing its window entirely during a long `waitForExistence`

None of these are assertion failures, and no Scarf crash reports are produced. The journeys already carry the mitigations that are available from the test side (documented in the memory note "XCUITest input and click reliability on macOS: what actually works"): re-activate before each interaction phase, retry clicks with an observable outcome, verify typed text and retype, keep sentinel strings short, keep waits proportionate. Those took a 4-failure run to 0 failures — but they cannot fix an app that loses its helper connection.

This matters because the gate is meant to run inside `release.sh`, where an intermittent red blocks a release and trains people to pass `--skip-ui-tests`.

Worth investigating:
- Whether the failures track machine load specifically (run the suite on an idle Mac N times and count), which would make a dedicated/quiet runner the answer rather than more test-side retries.
- Whether `gracefulQuit` is fully draining Scarf between tests — 5 launch/quit cycles per invocation, each spawning `hermes` subprocesses, and the degradation is monotonic within an invocation.
- Whether the suite should be split so fewer app launches share one `xcodebuild test` invocation.
- A retry policy for infrastructure-class failures only (XCTest's `-retry-tests-on-failure` with `-test-iterations`), which must NOT be allowed to paper over assertion failures.

Do not "fix" this by loosening assertions.
