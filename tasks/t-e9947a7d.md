**A10 — LIKE fallback.** New `ScarfCore/Services/HermesSearchIndex.swift` holds the whole `messages_fts` contract (`HermesFTSIndex`: 8192 prefix, the high-water key, the two rebuild keys, the scan budget) plus `HermesSearchIndexStatus`. `HermesDataService.searchMessages` keeps its MATCH SQL byte-identical and, only when the `state_meta` marker is present AND the MATCH pass under-filled the limit, tops up with a bounded LIKE scan over `role='tool' AND id > highWater AND length(content) > 8192` under the same active/compacted clause, merged by id. Off the main actor (actor-isolated, as before). Terms are LIKE-escaped (`ESCAPE '\'`), capped at 8.

**Timing, on a 1.6 GB fixture** (20k messages, tool payloads 2 KB–250 KB, needle at the tail of a 250 KB row, warm cache, `sqlite3 -readonly`):

| candidate budget | bytes read | match | no match |
|---|---|---|---|
| 400 (shipped) | 41.7 MB | 0.06–0.10 s | 0.08–0.09 s |
| 2000 | 208.5 MB | 0.28–0.33 s | 0.47–0.60 s |

Cost is flat in match-vs-miss and does not grow with state.db size — that is the point of bounding by rows read rather than rows returned.

**A10b — rebuild affordance.** `searchIndexStatus()` reads `fts_rebuild_progress` / `fts_rebuild_high_water`; `SessionsViewModel.searchIndexRebuilding` drives a one-line note above the search results. **Correction to the finding:** those keys are NOT v0.21.1 and there is no one-time full rebuild at first v0.21.1 open — `_migrate_bounded_tool_fts_triggers` (hermes_state_schema.py:287-291) swaps the triggers without rebuilding, and the keys first appear at v2026.7.30 (opt-in `sessions optimize-storage`). So the note is key-presence-gated with no version floor, which is also correct for a pre-0.21.1 host mid-optimize. Only `FTS_TOOL_CONTENT_PREFIX_CHARS` / `fts_tool_full_content_high_water` are genuinely v2026.9.7 (commit 57162d0cc1).

**A12 — NOT just a verification; a real bug, fixed.** `LocalSQLiteBackend.refresh(forceFresh: false)` keeps its handle (the gh#102 fix), and a sqlite connection follows the inode — so after `quarantine_zeroed_state_db` renames state.db aside and a fresh one lands at the same path, Scarf served the quarantined file for the rest of the process's life, silently. Now compares `(st_dev, st_ino)` against the identity recorded at open, with `st_ino == 0` treated as UNKNOWN (mirrors Hermes's `stat_db_file_identity`). The WATCHER half needed no change: `HermesFileWatcher` already re-arms on `.delete` and re-opens by path (verified against `architecture/a-vnode-watch-dies-on-the-first-atomic-replace-unless-it-re`). Regression-checked: the new test fails with the identity check removed.

**Schema tests.** `HermesV0211SchemaTests` — v2026.9.7 DDL transcribed from `hermes_state_common.py` (sessions +`tool_names` +`compression_recovery_deadline`, `conversation_generations`, `idx_sessions_effective_activity`), asserts every probe lands, every column Scarf's real read paths select exists, the `messages` DDL is unchanged from v0.21.0 (24 columns, pinned), and `sessions.tool_names` decodes as a JSON array. No UI.

**Tests.** `HermesV0211SearchIndexTests` (12), `HermesV0211SchemaTests` (4), `HermesStateDBReplacementTests` (3). ScarfCore 2372/2372, app target 832/832. `ACPClientStartIdempotenceTests` flaked under full parallel load and passed 5/5 in isolation.

**Deliberate NO-OPs.** No `messages_fts` UI beyond the one-line note. No `sessions.tool_names` decode into `HermesSession` (schema test only — the task marked it optional and there is no consumer).
