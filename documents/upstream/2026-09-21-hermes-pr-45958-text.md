## A. PR description

## What does this PR do?

Lets an ACP client choose the tool surface of each session, and adds the `hermes acp --toolsets` flag the ACP command never had.

An ACP client commonly drives **one long-lived `hermes acp` process for many projects**. Every session in that process is built from a hardcoded `["hermes-acp"]` (`acp_adapter/session.py`, `_make_agent`), so a project that should run with a narrower surface has no lever.

Two levers, one seam:

- **Per process:** `hermes acp --toolsets file,web` (`-t`), mirroring `hermes chat -t`.
- **Per session:** `session/new` accepts `_meta.hermes.toolsets` (JSON array, or a comma-separated string) — the namespace `acp_adapter/provenance.py` already uses for Hermes's own `_meta`. `session/load` and `session/resume` accept it too, where it re-scopes a session being restored from `state.db`.

Resolution is a single expression in `_make_agent`: the session's selection, else the process default, else exactly what main does today. **Pass neither and nothing changes** (pinned by a test, including the persisted `model_config` blob gaining no key).

**A scoped session never silently widens.** The selection lives on `SessionState`, rides through the `/model` rebuild (main already forwards the live agent's `enabled_toolsets`; this PR adds the regression test), is persisted in the existing `model_config` JSON (base names only — never the expanded `mcp-*` entries, so a restore cannot resurrect toolsets for servers that are gone), is inherited by `fork_session`, and MCP servers attached to the session still layer on top. No schema change.

**Bad input is an error, not a fallback.** A `_meta.hermes.toolsets` that is present but unusable — `[]`, a non-array, an unknown name — returns `invalid_params`. A client that meant to narrow is never handed the full default instead. (This is deliberately the opposite of the empty-result fallback flagged in the review of #70326.) Validation runs off the event loop, in front of the existing off-loop session construction (#58083), and a test pins that.

### This addresses both points from the review of the previous version

1. *Override lost on `/model` rebuild; `SessionState` did not retain it* — it is now on `SessionState`, and a test drives the real `_switch_model` path. The same hole existed on restore-from-DB and fork; both are closed and tested.
2. *`--toolsets` was forwarded but never declared on the live parser* — declared in `hermes_cli/subcommands/acp.py` and `acp_adapter/entry.py`; a test goes through the real `hermes` argparse tree into `HermesACPAgent(default_toolsets=…)`.

### How this relates to the other open ACP toolset PRs

#106834, #111575, #37842, #46832, #82546 and #70326 all change how the **process/profile-wide base** is resolved (config `platform_toolsets.acp`, plugin toolsets, the shared `_get_platform_tools` resolver). They fix real problems this PR does not touch — `hermes tools disable` being ignored under ACP, plugin tools never reaching the model.

This PR is the **per-session layer on top of whatever base is resolved**, and it implements none of their config resolution. Config cannot provide per-session scoping: it is per-profile and global, while one ACP process serves many sessions at once; rewriting `config.yaml` per chat would race between concurrent sessions and mutate the user's own settings.

Composability was tested, not assumed: with #106834 rebased onto current main and this commit cherry-picked on top, there is exactly **one conflict hunk**, resolved as

```python
else _expand_acp_enabled_toolsets(
    self._session_toolsets(toolsets) or _acp_base_toolsets(config), ...)
```

— per-session scope when present, their resolved base otherwise. Happy to rebase onto whichever of those lands first.

### Things a reviewer should know

- `-t` on `hermes acp` also reaches the existing `set_mcp_server_filter(args.toolsets)` call in `hermes_cli/main.py`, exactly as `hermes chat -t` does: it narrows which **config-declared** MCP servers are spawned at startup. MCP servers an editor attaches per session over ACP are unaffected. The subparser uses `default=SUPPRESS`, so without the flag the filter is untouched.
- The CLI flag does not validate names, matching `hermes chat -t`. The `session/new` path does validate, because it is a programmatic surface where a typo should be a protocol error.
- This is a configuration knob for a trusted host, not a sandbox: any registered name is accepted, so `all` widens past the curated `hermes-acp` set. The docs say so in a warning. There is no untrusted-host mode in `acp_adapter/` that this would undermine; `permissions.py` and `approvals.*` are untouched.
- A restored session whose persisted scope names a toolset that no longer resolves (e.g. a removed plugin) is not restored: `session/load`/`resume`/`prompt` return `-32603` with `Session <id> is scoped to unknown toolset(s): …` and a WARNING is logged — rather than silently widening to the default or building a zero-tool agent that still accepts prompts. An explicit `_meta.hermes.toolsets` on the call still opens it. (`return None` was not truthful: `load_session` returning `None` yields a bare `{"result": {}}`, indistinguishable from success.)
- `-t` on `python -m acp_adapter.entry` now applies the same `set_mcp_server_filter` as the `hermes acp` launcher (it previously did not — same flag, two behaviours).
- A client `-32602` is logged as one WARNING line instead of a "Background task failed" traceback (`_BenignProbeMethodFilter` widened).
- Not done here, worth follow-ups if you agree: (1) expose a session's scope in the `_meta.hermes` response so a client can verify what it asked for; (2) config-declared `mcp-*` servers still ride on top of a narrowed session — documented as-is, but it should be a decision; (3) the zh-Hans docs mirror.
